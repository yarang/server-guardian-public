# 코드 읽기 구조 변경 검토: Agentic MapReduce 제안 (2026-10-12)

[English](2026-10-12-retrieval-architecture-review.md) | 한국어

> 2026-10-12 시점의 기록이며, 이후 코드가 바뀌었다.

## 배경

사용자가 공유한 제안은 "결정론적 인덱싱 → 샤딩 → 에이전트 Map → 교차검증 Reduce"를 업계가 수렴하는 방향으로 소개한다. 그래프 DB와 벡터 인덱스를 공유 상태로 두고, 작업 큐와 여러 대의 워커 서버를 쓰는 다층(L0~L4) 구조다.
근거로 Cognition의 보안 스캔, Cursor의 planner–worker, Aider RepoMap·RepoGraph·CodexGraph·LocAgent, Agent4cs·Meta-RAG, Code Broker를 든다.
이 제안을 server-guardian에 적용할지 4명의 팀으로 검토했다.

| 역할 | 관점 |
|---|---|
| 설계자 | 이 시스템에 맞는 최선의 발전안 |
| 비판자 | 제안과 현재 계획을 똑같이 공격, 보안 |
| 운영 | 허브·플릿의 실제 운영 조건과 비용 |
| 판정자 | 세 의견과 쟁점을 코드로 사실 확인한 뒤 결정 |

제안이 인용한 출처(ZenML 요약 페이지, arXiv 번호)는 이번 검토에서 원문을 확인하지 않았다. 수치(읽기·검색이 tool-use 턴의 56.2%, 토큰의 46.5%)는 전체 코드베이스 보안 스캔이라는 다른 작업에서 나온 값이다.

## 결론

단일 허브의 도구 기반 토론 탐색을 유지하고 P1 → P2 → P3를 계속한다. 제안의 분산 구조는 채택하지 않는다(그래프 DB, 벡터 인덱스, 큐, 다중 서버 워커, tree-sitter·SCIP).
세 역할이 모두 같은 결론을 냈고 사실도 이를 뒷받침한다.

- 저장소가 작다(479개 파일, 4.2MB).
- LLM은 구독형 CLI라 워커를 늘려도 같은 계정의 속도 제한을 나눠 쓴다.
- 허브는 2 OCPU·12GB이고 Gitea와 다른 앱도 함께 돌린다.
- 사용자가 표준 라이브러리만 쓰기로 정했다.
- 병목은 처리량이 아니라 "어디를 읽을지 모름"에서 오는 과다 읽기(한 단계 1,301개 항목, 5.6MB)다.

제안에서 가져오는 것은 모두 현재 구조 안에서 가볍게 구현한다.

- 결정론적 인덱스와 MCP 노출: P1에서 완료(`defs`/`refs`, `repo_defs`/`repo_refs`)
- 저장소 지도: P2(진행 중)
- 별도 검증 단계: LLM이 아닌 결정론적 인용 대조(P2.5)
- 작업 키: `prompt_version`/`map_version` 메타데이터(P2)
- 컴파일러 보조 인덱스와 `callers`/`callees` op: Go부터, 허브의 Go 툴체인으로 타입 검사(P2.6, 2026-10-12 사용자 결정으로 표준 라이브러리 import 그래프 대신)
- MapReduce·셀렉터·샤딩: P3 뒤 허브 안의 감사 작업으로(사용자 결정 2)

비판자가 찾은 P1의 결함은 모두 사실로 확인됐다(아래 "사실 확인"). 다만 어느 것도 MapReduce를 정당화하지 않으며 현재 설계 안에서 고친다.

## 사실 확인 (P1 커밋 `98e0be7` 기준)

| 쟁점 | 결과 | 근거 |
|---|---|---|
| (a) 캐시가 소스 텍스트를 저장하지 않는다는 docstring | 사실과 다름. 선언 첫 줄을 `signature`(200자)로 저장하고, 모듈 수준 대입(`API_KEY = "..."`)도 선언이다. 같은 내용은 grep·read로 이미 LLM에 가지만, 정리되지 않는 사본이 디스크에 남는다 | `code_index.py:30-31`, `:63-65`, `:106-111`, `:452-474` |
| (b) grep/`refs` 결과의 파일 전체가 "제공됨"으로 셈 | 사실. `refs` 최대 200줄. grep도 P1 이전부터 같았다 | `repo_tools.py:173-176`, `:46`, `:574-577`, `debate_engine.py:1443-1444`, `:1148-1149` |
| (c) `refs`의 조용한 거짓 음성 | 사실. 파싱 실패, 1MB 초과, 식별자당 5000줄 상한을 알리지 않는다 | `repo_tools.py:572-573`, `code_index.py:524-526`, `:487-489`, `:51`, `:70` |
| (d) `is_secret`이 파일 이름만 검사 | 사실 | `code_context.py:27`, `:115-117`, `repo_tools.py:245-247` |
| (e) 비판자 병렬 실행 | 사실(패널일 때만). Expert·Judge는 순차 | `debate_engine.py:759-763` |

## 수정된 로드맵

1. **평가 1차는 고정한다.**
   - `map` 구성은 P2 커밋 그대로 쓴다. 에이전트가 보지 않는 메타데이터(`prompt_version`/`map_version`)와 docstring 정정만 함께 들어간다.
   - 판단 기준은 계획에 미리 적은 규칙이다. 설계자가 낸 "바이트 30% 감소" 기준은 사후에 덧붙이지 않고 평가 2차 목표로 둔다.
2. **P2.1, 견고성:** W2, W4(문자열 가림과 `INDEX_VERSION` 올림), W5, W4b(사용자 승인 시)
   - 끝 조건: 결과 끝 표시의 모든 경우에 테스트가 있다.
   - 끝 조건: 캐시의 `signature`에 문자열 리터럴이 남지 않는다.
   - 끝 조건: `config/secrets/x.yaml`을 읽을 수 없다.
3. **P2.5, 근거:** 줄 범위 기반 인용 검증과 `findings[]` 인용 대조. 이벤트는 `evidence_check{checked, mismatched}`
   - 끝 조건: 같은 이름 `Handle` 미끼를 잡는다.
   - 끝 조건: provider별로 `findings[]`를 낸 비율을 보고한다.
4. **P2.6, Go 컴파일러 보조 인덱스:** 임시 작업 트리에서 `go list -export`와 `go/types`로 사실을 뽑고 작업 트리와 산출물을 지운다. `callers`/`callees`는 근거로 세지 않는다. 설계는 `docs/design/debate-code-index-wiki.md`의 "1층 확장".
   - 끝 조건: B1~B3·E2의 정답 일치가 P2.1보다 같거나 낫다.
5. **P3, 위키(설계대로):** 키는 basis blob과 `prompt_version`이다. 전용 작업 슬롯을 두고, 캐시를 정리하며, 폴백 응답으로는 페이지를 쓰지 않는다.
   - 끝 조건: 미끼 2를 통과하고, 위키만 보고 쓴 인용이 하나도 남지 않는다.
6. **평가 2차:** 12문항에 E1~E3을 더하고 각각 3회 반복한다. 단계별 토큰, 속도 제한 횟수, 미검증 인용 수를 기록한다.
   - E1: `apps/agent`의 모든 HTTP 라우트와 인증 래퍼. grep으로 만든 정답 대비 정밀도·재현율로 잰다.
   - E2: Go 에이전트에서 Python으로 넘어가는 모든 경로
   - E3: 존재하지 않는 기능을 묻는 질문(거짓 주장 측정)
7. **감사 작업(사용자 결정 2):** P3 뒤에 설계를 시작한다. 허브 안에서 순차로 돌고, 작업 키로 체크포인트를 둔다. 커버리지는 셀렉터가 아닌 독립 정답(E1 방식)으로 잰다. 평가 2차의 E1 결과를 설계 입력으로 쓴다.
8. **조건이 생길 때만:** 판정자 검증에 정적 분석
