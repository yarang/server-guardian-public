# 흐름 그래프: 다이어그램에 캐릭터 앉히기 (설계)

[English](flow-graph.md) | 한국어

상태: 2026-11-01 결정. 결정 D1-D8과 용어는 2026-11-01 대화에서 운영자와 정했다. 아무것도 만들지 않았다. 편집기
라이브러리는 같은 날 정했다(D9). 이 설계는 [team-flows.md](team-flows.ko.md)의 결정 1과 하지 않는 것 "임의 그래프",
[flow-templates.md](flow-templates.ko.md)의 "임의 그래프가 아니다"라는 문장을 바꾸고, 팀과 템플릿 층을 대신한다
("이전 결정에서 바뀌는 것" 참고).

## 문제

지금 업무 흐름 하나를 만들려면 다섯 층을 거치고, 층마다 고치는 곳이 다르다.

```
캐릭터(페르소나)  ->  팀(누가 어느 자리에 앉는지)  ->  팀 흐름 종류(debate, panel, verify, pipeline, versus)
                  ->  흐름 템플릿(단계, 매개변수, 과제 문안)  ->  시작 양식(매개변수 값)
```

흐름 종류 탭(T3b)이 이것을 그대로 보여 준다. 먼저 "모양"(기존 흐름 종류 하나, 또는 사용자 정의 단계)을 고르고, 자리가
암묵적으로 정해지는 단계를 고르고("초안은 전문가 1명, 동시 초안은 전문가와 모든 제안자, 비평은 모든 비평가"), 다른
칸에서 팀을 고른 뒤에야 미리보기가 실제로 누가 도는지 보여 준다. 복잡하게 느껴지는 이유는 세 가지다.

1. **순서가 보이지 않는다.** 흐름은 단계 이름의 목록이고, 누가 누구를 읽는지는 단계 종류와 팀에 숨어 있다.
2. **무엇이 전달되는지 보이지 않고 고를 수도 없다.** 단계마다 박혀 있다. 동시 초안은 순서를 바꾸는 라벨을 붙이고,
   파이프라인은 앞 결과의 사슬을 그대로 넘기고, 비평은 판정자에게 원문 그대로 이어 붙여 가고, 이전 라운드는 16 KiB를
   넘으면 압축한다(`thread_digest.py`).
3. **용어가 의미가 아니라 입력칸을 가리킨다.** 매개변수 종류 "한 줄 글"(`string`)과 "여러 줄 글"(`text`)은 입력칸
   모양, 줄바꿈 허용, 길이 한도만 다르다. 둘 다 `${NAME}`으로 과제 문안에 들어간다. 언제 무엇을 써야 하는지 알려 주는
   것이 없다.

## 목표

운영자가 캔버스에 캐릭터를 앉히고 연결해서 흐름을 만든다. 배치와 연결이 순서의 전부이고, 자리가 앞 결과를 어떻게
받는지는 그 자리의 설정이다. 흐름은 한 가지 업무가 아니라 **일하는 방식**(작성, 병렬 검토, 정리, 판정)을 나타내므로,
같은 흐름을 여러 업무와 프로젝트에 쓸 수 있다.

## 용어

"노드"는 이미 플릿의 머신을(`docs/glossary.ko.md`), "노드 그룹"은 머신 묶음을, "게이트"는 jev 게이트와 배치 게이트를
뜻한다. 그래서 다이어그램에는 다음 말을 쓴다.

| 한국어 | 영어와 코드 | 뜻 |
|---|---|---|
| 흐름 | flow | 다이어그램: 자리, 연결, 매개변수, 과제 문안 |
| 자리 | seat (`seats`) | 다이어그램에서 캐릭터가 일 하나를 하는 곳 |
| 캐릭터 | character | 자리에 앉는 이([agent-characters.md](agent-characters.ko.md)) |
| 맡은 일 | job | 자리가 하는 일: 작성 write, 비평 critique, 다시 쓰기 rewrite, 반론 rebut, 정리 summarise |
| 동시 묶음 | bundle (`bundles`) | 병렬로 도는 자리들 |
| 마감 | close (`close`) | 공통 마감: 판정자, jev 게이트, 조치 검사. 흐름마다 하나 |
| 시작, 끝 | start, end | 다이어그램의 고정된 양 끝 |
| 연결 | link (`links`) | "이 자리가 저 자리를 읽는다" |
| 되돌아보기 연결 | look-back link | 이전 라운드를 읽는 연결 |
| 거부 시 돌아갈 곳 | rejected exit | REJECTED 뒤에 다음 라운드가 시작하는 곳 |
| 라운드 | round | 시작(또는 거부 시 돌아갈 곳)에서 마감까지 한 번 도는 것 |
| 받는 방식 | input mode | 원문 raw, 요약 condensed, 핵심만 structured, 최신만 latest |
| 정리자 | summariser | 맡은 일이 정리인 자리 |

캐릭터 파일의 `seats` 필드(expert, critic, judge, ...)는 그 캐릭터가 맡을 수 있는 일의 목록이다. 대시보드는
"맡을 수 있는 일"로 보여 주고, 파일 키는 호환을 위해 그대로 둔다.

| D5 | **첫 배포에 편집기를 포함한다.** 단계로 나눠 만들고 한 번에 배포한다. |
| D6 | **자리는 캐릭터와 맡은 일의 조합이다.** 맡은 일은 닫힌 목록에서 고른다. 맡은 일이 엔진의 역할 카드([agent-characters.md](agent-characters.ko.md) 4장)와 그것을 실행할 단계 조각을 정한다. 자리는 일반적이고, 하는 일은 엔진이 테스트한 조각으로 남는다. 용어는 위와 같다(D6a). |

| D8 | **글 매개변수는 한 종류다.** 편집기는 글, 숫자, 목록에서 선택 세 가지를 보여 준다. 입력칸 모양은 최대 길이를 따른다. 200자 이하는 줄바꿈 없는 한 줄 입력칸(`string`으로 저장), 넘으면 여러 줄 입력칸(`text`로 저장)이다. 파일과 엔진은 원래 네 타입을 유지하고, 기존 파일은 그대로 읽힌다. |
| D9 | **편집기는 `@xyflow/react`를 쓴다**(이동, 확대, 손잡이, 선 경로, 키보드 접근). 다른 웹 의존성처럼 정확한 버전으로 고정하고, 버전은 G4에서 고른다. 의존성 없는 SVG 편집기 직접 구현은 택하지 않았다. |

## 모델

### 요소

| 요소 | 개수 | 하는 일 |
|---|---|---|
| 시작 | 1 | 과제 문안, 매개변수, 기본 코드 컨텍스트. 모델 호출 없음 |
| 자리 | 1개 이상 | 맡은 일 하나, 제공자, 코드 도구, 선택적 한 문장 초점을 가진 캐릭터 하나. 라운드마다 모델 호출 1회 |
| 동시 묶음 | 0개 이상 | 안의 자리들이 병렬로 도는 틀. 출력은 이번 라운드에서 그 자리들이 쓴 것이고, 지금의 동시 초안처럼 라운드마다 순서를 바꾸는 중립 라벨(`A`, `B`, ...)을 붙인다 |
| 마감 | 정확히 1 | 공통 마감. 캐릭터는 판정자 자리에 앉는다. `allowed_tools`는 지금처럼 프로젝트가 좁힌다. 출구 두 개: 승인과 거부 |
| 끝 | 1 | 결과와 기록된 조치 |

맡은 일과 다시 쓰는 기존 조각:

| 맡은 일 | 지금의 단계 조각 | 역할 카드 |
|---|---|---|
| 작성 | `_step_draft` (`draft`, 동시 묶음 안에서는 `blind_draft`) | expert |
| 비평 (반대 의견 또는 체크리스트) | `_step_critique` | critic 또는 verifier |
| 다시 쓰기 | `_step_rewrite` (파이프라인 단계, 거부 뒤의 리드) | stage |
| 반론 | `_step_exchange` (versus) | side |
| 정리 | 새로 만듦("정리자" 참고) | 없음, 지시문을 생성 |

반론을 맡은 자리는 입장을 갖는다. 입장은 매개변수나 고정 문장에서만 오고 모델에서 오지 않는다(`flow-templates.md`
결정 4 유지). 정리자 자리에는 캐릭터가 필요 없다.

### 연결

- **연결**(실선): `A -> B`는 B가 A의 출력을 읽는다는 뜻이다. 앞으로 가는 연결은 순환이 없어야 하고, 이것이 순서가 된다.
- **되돌아보기 연결**(점선): 뒤로 가는 연결. B는 A의 **이전 라운드** 출력을 읽는다. 작성자가 지난 라운드의 비평을
  읽는 것이 되돌아보기 연결이다.
- **거부 시 돌아갈 곳**: 다음 라운드가 시작하는 곳. 그곳에서 닿는 자리만 다시 돈다. `max_rounds`를 갖는다.
  "2라운드부터는 리드만"은 리드로 돌아가는 것이다.
- **승인 출구**: 끝으로 간다.

### 검증

Python이 유일한 검증자로 남는다(`flow_graph.py`, 새로 만듦). Go는 전달만 하고, 대시보드는 템플릿처럼 같은 검사를 따라
해서 첫 문제를 먼저 알려 준다.

- 시작, 마감, 끝은 하나씩. 모든 자리가 마감에 닿는다. 마감의 두 출구가 모두 연결돼 있다.
- 앞으로 가는 연결은 순환 없음. `max_rounds` 1-10. 마감의 판정 말고 다른 분기 없음(`team-flows.md`의 하지 않는 것 유지).
- 동시 묶음은 자리 1-4개. 병렬 호출은 `GUARDIAN_MAX_PARALLEL_AGENTS`로 제한. 자리는 12개까지이고 라운드당 모델 호출
  수 상한이 있으며, 넘으면 저장할 때 거부한다.
- 정리자는 정확히 한 자리(또는 마감)에 넘긴다.
- 캐릭터가 맡을 수 있는 일이 그 자리의 일을 허용해야 한다(C2 자리 검사). 시작할 때 바꿔 앉힌 캐릭터도 같다.
- ops와 design 프로젝트: 도구는 프로젝트가 좁히고 design은 자동 적용하지 않는다. 어떤 흐름을 돌릴 수 있는지는
  템플릿처럼 시험을 거친 뒤 흐름마다 정한다.

## 공통 출력 형식

마감을 뺀 모든 자리는 같은 모양으로 답한다. 내용은 업무마다 다르지만 모양은 같으므로, 뒤 자리를 업무를 모른 채로
정의할 수 있다.

```
## Conclusion        한두 문장
## Claims            - 주장마다 한 항목
## Evidence          - path:line-line  인용한 줄   (정리자가 원문 그대로 보존)
## Open issues       - 해결되지 않았거나 결정이 필요한 것
## Recommendation    선택
```

변환된 팀과 템플릿이 바이트 단위로 같아야 하므로(T2의 golden gate), 형식 규칙은 어딘가에 요약이나 핵심만을 쓰는
흐름에만 들어간다. 그런 흐름은 새 프롬프트 버전을 받는다(`RETRIEVAL_PROMPT_VERSION` 올림). 제목이 빠진 답은
`format_retry`를 한 번 받고, 그 뒤에는 그대로 넘기되 `envelope: false`로 표시하며 받는 자리는 그 답을 원문으로 받는다.

## 받는 방식 (받는 자리에 둠)

| 방식 | 자리가 받는 것 | 추가 호출 |
|---|---|---|
| 원문 (기본) | 읽는 자리들의 출력 전체, 지금과 같음 | 없음 |
| 요약 | 앞에 놓인 정리자의 출력 | 라운드마다 1회 |
| 핵심만 | 각 입력의 `Conclusion`, `Claims`, `Evidence`, `Open issues`만, 규칙으로 잘라냄 | 없음 |
| 최신만 | 원문과 같지만 되돌아보기 연결은 마지막 라운드만 전달 | 없음 |

연결에 `blocked`를 걸면 그 입력이 빠진다. 자리마다 이전 라운드를 어떻게 볼지 **기록** 설정도 있다: digest(기본,
지금의 스레드 digest), full, none. 지금의 `_format_history`처럼 새 CLI 세션에서 의미가 있다.

편집기에서 자리를 고르면 그 자리가 받을 것을 보여 준다. 읽는 자리들, 각각의 방식, 마지막 실행의 글 크기다.

## 정리자

정리자는 입력의 내용을 모르고, 알 필요도 없다. 입력의 **모양**(공통 형식)과 자기가 넘겨줄 자리의 **목적**을 알기
때문이다. 지시문은 흐름에서 만든다.

```
You condense work for the next step. The next step's task is:
  «받는 자리의 맡은 일, 캐릭터 요약, 초점»
Keep what that task needs. For each input:
- Conclusion and Claims: compress, merge duplicates across inputs, keep who said what (label).
- Evidence: copy every citation line unchanged; drop none that supports a kept claim.
- Open issues: keep all of them.
Drop reasoning steps, repetitions and politeness. Use the same envelope headings.
```

그래서 같은 흐름이 보안 리뷰, 운영 점검, 문서 검토에 모두 동작하고, 받는 자리가 바뀌면 정리도 따라 바뀐다.

규칙 기반 검사:

- 요약에 있는 모든 인용은 입력 가운데 하나에 원문 그대로 있어야 한다. 아니면 요약을 버리고 받는 자리는 그 라운드에
  원문을 받는다(이벤트 `summary_rejected`).
- 요약이나 핵심만 받은 자리는 인용된 줄을 직접 보지 않았다. 요약에서 옮겨 적은 인용은 약한 근거이고, 새로 단 인용은
  지금처럼 line-span 규칙을 따른다.

## 실행

- `flow_graph.py`가 흐름을 T2 해석기(`_flow_steps`)가 이미 돌리는 단계 목록으로 바꾸고, 받는 방식과 정리자 단계를
  더한다. 팀 흐름 종류나 템플릿에서 변환한 흐름은 지금 `_steps_of`와 `engine_steps`가 만드는 것과 같은 단계 목록을
  내야 한다(golden dump 변화 없음).
- transcript 항목과 에이전트 이벤트에 `step`, `stage`, `side` 옆에 `seat`(자리 id)가 붙는다. 역할은 `Domain Expert`,
  `Critic Agent`, `JEV-MCP Judge`를 그대로 써서 리포트, `jev`, 감사가 옛 스레드와 새 스레드를 똑같이 읽는다.
- 세션 키 `(thread_id, role)`는 그대로. 새 흐름의 자리는 `role = "seat:<id>"`를 쓴다.
- `UNVERIFIED`는 지금처럼: 마감으로 이어지는 자리가 하나라도 대체 답을 내면 그 라운드는 `UNVERIFIED`다.
- 스레드 스냅숏은 흐름 id, 흐름 글의 해시, 실제로 앉은 캐릭터(바꾼 뒤), 매개변수 값을 저장한다. 나중에 흐름을 고쳐도
  시작한 스레드는 바뀌지 않는다.

## 저장과 변환

기본 제공은 `configs/flows/*.json`, 운영자 것은 `<GUARDIAN_DATA_DIR>/flows/*.json`. 사용자 정의 파일이 같은 id의 기본
제공 파일을 가리고, 서버가 `created`와 `modified`를 찍는다(팀과 템플릿의 규칙).

```json
{
  "id": "review-two-stage",
  "name": "Two-stage review",
  "category": "development",
  "projects": ["code"],
  "params": {"TARGET": {"type": "string", "label": "Target", "max": 200}},
  "task": "Review ${TARGET}.",
  "seats": [
    {"id": "lead", "job": "write", "character": "guardian_lead_dev", "providers": ["claude"]},
    {"id": "sec", "job": "critique", "character": "guardian_security_critic", "providers": ["codex"]},
    {"id": "qa", "job": "critique", "mode": "checklist", "character": "guardian_qa_critic", "providers": ["agy"]},
    {"id": "sum", "job": "summarise", "providers": ["claude"]}
  ],
  "bundles": [{"id": "review", "seats": ["sec", "qa"]}],
  "close": {"character": "guardian_dev_judge", "input": "condensed", "allowed_tools": ["jev_mcp:run_tests"]},
  "links": [
    {"from": "start", "to": "lead"},
    {"from": "review", "to": "lead", "look_back": true},
    {"from": "lead", "to": "review"},
    {"from": "review", "to": "sum"},
    {"from": "sum", "to": "close"},
    {"from": "close", "to": "lead", "exit": "rejected", "max_rounds": 3},
    {"from": "close", "to": "end", "exit": "approved"}
  ],
  "layout": {"lead": [240, 80], "review": [480, 40]}
}
```

`start`, `close`, `end`는 고정 id다. `layout`은 캔버스 위치만 담고 실행을 바꾸지 않는다.

읽을 때 변환(`team_to_flow`, `template_to_flow`)하므로 기존 것은 깨지지 않는다.

| 지금 | 흐름 |
|---|---|
| `debate` | 시작 -> 리드(작성) [+ 제안자 동시 묶음, 서로 blocked] -> 비평가 동시 묶음 -> 마감. 비평가 -> 리드 되돌아보기. 거부 시 리드로 |
| `verify` | `debate`와 같고, 비평가는 체크리스트 방식 |
| `panel` | 시작 -> 동시 묶음(리드 + 제안자, 작성) -> 마감. 라운드 한 번 |
| `pipeline` | 시작 -> 단계 1(작성) -> 단계 2(다시 쓰기) -> ... -> [비평가] -> 마감. 거부 시 리드(다시 쓰기)로 |
| `versus` | 시작 -> 동시 묶음(A측, B측, 작성, 입장) -> A측과 B측(반론, 서로 읽음) -> 마감 |
| 템플릿 | 변환된 팀의 흐름에 템플릿의 단계, 매개변수, 과제 문안 |

옛 스레드와 프로젝트의 `"team"` 키가 계속 동작하도록 팀과 템플릿은 계속 읽힌다. G4 뒤에 대시보드는 흐름만 편집한다.

## 편집기

업무 흐름 -> "흐름 종류" 탭이 흐름 편집기가 된다(`#/debates/templates`는 계속 열린다).

- **갤러리**는 지금처럼(목표별 카드) 두고, 카드마다 흐름을 작게 그린다.
- **캔버스**: 팔레트(자리, 동시 묶음, 정리자. 시작, 마감, 끝은 항상 있음). 끌어서 놓고, 손잡이에서 끌어 연결한다.
  뒤로 가는 연결은 되돌아보기 연결이 된다. 마감은 출구마다 손잡이가 하나씩 있다.
- **자리 패널**: 캐릭터(초상과 한 줄 소개가 있는 선택기, 맡은 일로 걸러짐), 맡은 일, 제공자, 코드 도구, 초점, 받는 방식,
  기록. 반론에는 입장. 마감 패널: 캐릭터, 받는 방식, 도구.
- **시작 패널**: 매개변수(글, 숫자, 목록에서 선택. D8)와 과제 문안. 지금 템플릿 편집기와 같은 검사.
- **미리보기**: 라운드당 호출 수, 고른 자리가 받을 것.
- **검증**은 바뀔 때마다 돌고 자리와 연결에 표시한다. 오류가 남아 있으면 저장을 거부한다.
- **시작 화면**: 흐름을 고르고, 매개변수를 채우고, 필요하면 자리별로 캐릭터를 바꾸고(D7), 라운드 수를 고른다.
- **보기 화면**: 토론 결과와 Agents 모니터가 같은 흐름을 그리고 실행된 자리를 상태별 색으로 칠한다.
- 좁은 화면에서는 보기 화면과 목록 편집기(자리와 읽는 자리를 양식으로)를 쓴다.
- 문구는 두 카탈로그(`ko`, `en`)에 넣고, 새 용어는 `docs/glossary.ko.md`에 넣는다.

라이브러리: `@xyflow/react`(D9). 자리, 동시 묶음, 마감, 시작, 끝은 사용자 정의 노드 컴포넌트이고, 되돌아보기 연결과
마감의 두 출구는 사용자 정의 선 종류다. 보기 화면은 같은 컴포넌트를 편집 없이 쓴다.

## 이전 결정에서 바뀌는 것

- `team-flows.md` 결정 1과 하지 않는 것 "임의 그래프": 이제 흐름은 자리의 그래프다. 남는 것: 공통 마감, 필수 판정자,
  모델 출력에 따른 분기 없음, 판정자 판정을 통한 루프만, 검색 말고 단계 안의 도구 없음.
- `flow-templates.md`와 `debate-teams.md`: 팀과 템플릿은 흐름으로 변환되는 입력이 된다(D7). `flow-templates.md`의
  결정 3, 4(공통 마감, 사람이 정하는 입장)는 유지.
- `debate-teams.md`의 "비평가 패널 발언은 원문 그대로 이어 붙인다": 여전히 기본값이다(D4). 운영자가 흐름 하나에서
  요약을 고를 수 있고, 그때 경고를 띄운다.

## 하지 않는 것

- 마감의 판정 말고 다른 조건, 거부 시 돌아갈 곳 말고 다른 루프.
- 마감이 아닌 곳의 도구나 조치.
- 팀 대 팀 토론, 구성원의 `host`가 이미 허용하는 곳 말고 다른 호스트에서 자리 돌리기.

## 열린 점

- 공통 형식의 정확한 문구, 첫 배포에 핵심만이 필요한지.

### G1 흐름 파일, 검증, 변환, 저장소 (2026-11-01 구현)

`cli/llm-agent/flow_graph.py`, 테스트 `test_flow_graph.py`, CLI `--flows`, `--flow-save`(stdin의 JSON),
`--flow-delete ID`(`config_ops.flows_report`, `save_flow`, `delete_flow`), 그리고 모든 기본 제공 팀과 템플릿이 검증을
통과하는 흐름으로 변환되는지 보는 `scripts/ci.sh config` 검사. 아직 흐름을 실행하지 않는다(G2). 허브 API는 G4다.
설계와 다른 점과 세부:

- **id.** 변환된 팀이 자기 id를 그대로 쓰므로 흐름 id는 팀 id 규칙(영문 소문자, 숫자, `-`, `_` 1-64자)을 따른다. 자리와
  동시 묶음 id는 같은 문자 1-32자이고 `start`, `close`, `end`는 쓸 수 없다.
- **맡은 일과 캐릭터 검사.** format 2 캐릭터는 그 일의 엔진 자리 하나를 갖고 있어야 한다: 작성 -> expert, proposer, stage.
  다시 쓰기 -> stage, expert. 비평 -> critic(반대 의견), verifier(체크리스트). 반론 -> side. 마감 -> judge. format 1
  페르소나는 자리 목록이 없어 통과한다. 한 캐릭터가 여러 자리에 앉을 수 있다(세션은 자리별로 둘 예정).
- **반론** 자리는 정확히 둘이 한 동시 묶음일 때만 있다. 그 묶음이 versus 팀처럼 `exchanges`(1-2)를 갖는다.
- **동시 묶음의 구성원**은 하나씩 연결할 수 있다(변환된 debate의 거부 출구는 `drafts` 묶음 안의 리드로 간다). 같은 묶음의
  구성원끼리는 서로 읽지 않는다.
- **선택 필드.** `projects`가 없으면 모든 프로젝트 종류, `task`가 없으면 시작할 때 사람이 과제를 쓴다(변환된 팀에는 없다).
  `context`는 팀 규칙을 쓴다.
- **한도.** 자리 12개, 묶음당 4개, 라운드당 모델 호출 16회(`calls_per_round`: 자리마다 1회, 반론 답마다 2회 더, 마감 1회).
- **정리자 규칙**은 G1에서는 구조만 본다: 정확히 한 자리나 마감에 넘기고, 요약 입력 앞에는 정리자가 있어야 하며,
  요약을 읽지 않는 자리에 넘기면 경고다. 지시문과 인용 검사는 G3다.
- **변환.** `team_to_flow`와 `template_to_flow`는 `_steps_of`와 `engine_steps`를 따른다: 리드(제안자가 있으면 `drafts`
  묶음), 비평가(패널이면 `critics` 묶음), 비평가(와 초안)에서 리드로 가는 되돌아보기 연결, 리드로 가는 거부 출구. 패널과
  비평이 없는 사용자 정의 템플릿은 바로 마감으로 가고 `max_rounds`는 1이다. 파이프라인의 리드는 거부 뒤에만 다시 쓴다
  (시작에서 연결되지 않음). versus의 두 측은 `sides` 묶음이 된다. 변환된 versus는 한 라운드 versus에서 돌지 않는 팀의
  `expert`를 뺀다. `converted_from`이 팀(과 템플릿) id를 갖고 있어 G2가 정확한 lineup을 찾을 수 있다.
- **보고.** `--flows`는 저장된 흐름, 템플릿, 팀을 흐름으로 나열한다(출처 `builtin`, `custom`, `template`, `team`, 각각
  `hash`, `calls`, `errors`, `warnings`). 저장된 흐름은 같은 id의 템플릿이나 팀을, 템플릿은 팀을 가리고 경고를 남긴다.
- **허브 확인(2026-11-01, 허브의 `teams`, `flow-templates`, `personas`를 읽기 전용으로 복사한 뒤 삭제).** 13개 모두
  변환되고 검증을 통과했다: 기본 제공 팀 8개, 사용자 정의 팀 5개(하나는 기본 제공을 덮어씀), 템플릿 `code-review`.
  경고는 기존의 고위험 도구 안내뿐이다.

### G2 흐름 실행 (2026-11-01 구현)

`flow_graph.compile_flow`, `swap_characters`, `resolve_run`, `find`, 엔진의 `run_debate(flow_run=...)`, CLI
`--debate ... --flow ID [--seat 자리=캐릭터] [--param KEY=VALUE]`. 관문은
`test_flow_golden.test_every_case_runs_the_same_from_its_flow`다. golden 37개 경우 모두, 팀을 흐름으로 변환했다가
다시 컴파일해서 시작해도 흐름이 더하는 필드를 빼면 팀 실행과 같은 dump를 낸다. 설계와 다른 점과 세부:

- **해석이 아니라 컴파일.** 흐름은 T2 해석기가 이미 돌리는 lineup(과 다섯 종류에 이름이 없는 모양이면 T3a의 사용자 정의
  단계)으로 컴파일된다. 알아보는 모양: versus 묶음, 파이프라인(단계 2-4개, 거부 뒤의 리드, 반대 의견 비평가 선택), 리드
  혼자 또는 제안자와 묶음, 한 가지 방식의 비평가 선택(debate, verify, panel, `draft`만, `blind_draft` + 체크리스트).
  다른 모양은 이름을 대고 거부한다("does not run yet"). G3 기능(정리자, 원문이 아닌 받는 방식, 기록 설정, blocked 연결,
  초점)도 거부한다.
- **세션 키는 lineup의 것을 그대로 쓴다**(리드, 페르소나별 패널 구성원, 단계와 측 위치). 계획했던 `seat:<id>`가 아니다.
  이어 가기와 golden dump가 그대로 유지된다. 그래서 한 캐릭터가 초안이나 비평가 묶음에 두 번 앉으면 실행할 때 거부한다.
- **versus에는 리드 자리가 없다.** 컴파일된 lineup은 A측 캐릭터를 대신 리드에 앉힌다(돌지 않음). lineup 스냅숏과
  `debate_started`의 구성원 목록에만 나타나므로, 관문은 versus에서 이 둘을 빼고 비교한다.
- **기록의 자리.** 구성원은 `seat`를 갖고(판정자는 `close`), transcript 항목과 에이전트 이벤트에 `step`처럼 최상위
  `seat`가 붙는다. lineup 스냅숏에는 `flow_graph`(id, 해시, 매개변수 값, 앉은 캐릭터, 있으면 사용자 정의 단계)가 붙고
  `debate_started`가 그 id를 적는다. 팀과 템플릿 실행은 바뀌지 않는다.
- **시작.** `--flow`는 저장된 흐름, 없으면 템플릿, 없으면 팀을 찾는다(변환, 보고서의 우선순위). 과제 문안이 있는 흐름은
  `--debate -`와 `--param`을, 없는 흐름은 과제를 받는다. `--seat`는 캐릭터를 바꿔 앉힌다(D7, 캐릭터가 그 자리의 일을
  맡을 수 있어야 함). 흐름은 새 스레드로 시작하고, `--team`, `--flow-template`, 역할별 덮어쓰기는 함께 쓸 수 없다.
  이어 가는 스레드는 `flow_graph`를 유지한다(사용자 정의 단계는 다시 검사).
- **하지 않음:** 허브 API와 흐름을 가리키는 프로젝트 `"team"` 키(G4).

### G3 공통 형식, 받는 방식, 정리자 (2026-11-01 구현)

`debate_engine.py`: `ENVELOPE_RULE`, `keep_sections`, `invented_citations`, `_close_material`(정리자),
`_carried_critique`. `flow_graph.compile_flow`는 `Compiled(team, steps, condense)`를 돌려주고, 흐름 기록에
`condense`(정리자, close_input, lead_input, envelope)가 붙는다. 프롬프트 버전 `p27`. 테스트: `test_flow_graph.py`
(`G3CompileTests`, `EnvelopeTextTests`, 인용을 지어낸 seeded 요약이 있는 `G3RunTests`). 설계와 다른 점:

- **도는 곳.** 정리자는 하나, 마감에 넘기는 단위와 마감 사이에서만(마감은 요약을 받음). 마감은 원문, 요약, 핵심만을, 리드는
  원문이나 핵심만을 받는다(핵심만은 다음 라운드로 가져가는 비평에 적용되고 초안에는 적용하지 않는다). 다른 자리의 받는
  방식, `latest`, 기록 설정, blocked 연결, 자리 초점은 "아직 만들지 않음"으로 거부한다.
- **정리자**는 라운드마다 한 번, 생성된 지시문(또는 자기 `instruction`), 판정자가 읽을 내용으로 묻고 스레드 기록은 주지
  않는다. 세션 키 `Summariser:<자리>`, transcript 역할 `Summariser`와 그 `seat`. 요약은 판정자에게 인용된 줄을 직접 보지
  않았다고 알리는 머리말과 함께 원래 내용을 대신한다.
- **인용 검사.** 요약의 인용(path:line, path:first-last, path#Symbol, ops 라벨 `[#...]`)이 원래 내용에 글자 그대로 없거나,
  정리자가 대체(canned) 답이나 빈 답을 내면 요약을 버리고 판정자는 원래 내용을 읽으며 `summary_rejected`(이유, 인용)가
  나간다. 버린 요약 때문에 라운드가 `UNVERIFIED`가 되지는 않는다. 원문과 다르게 쓴 범위도 지어낸 것으로 본다(안전한 쪽).
  판정자 자신의 인용에는 새 규칙이 필요 없다: 보지 않은 줄은 이미 line-span 검사에서 걸린다.
- **공통 형식.** 요약하거나 핵심만 받는 흐름에서는 판정자를 뺀 모든 자리의 규칙에 `ENVELOPE_RULE`이 붙는다. 다른 프롬프트는
  그대로다(golden dump 유지, 버전 표시만 `p27`). 제목이 빠진 답에 `format_retry`는 하지 않는다: `## Conclusion`이 없는
  글은 핵심만 입력에 그대로 들어간다.

### G4 허브 API, 편집기, 시작 화면, 보기 화면 (2026-11-01 구현)

Go: `GET/POST /api/flows`, `DELETE /api/flows/{id}`가 `--flows`, `--flow-save`, `--flow-delete`를 전달한다.
`POST /api/debates`는 `flow`와 `seats`를 받고(흐름은 `team`, `template`, `thread_id`를 거부, 과제는 선택, 매개변수는
템플릿과 같음) 작업 요약에 `flow`와 `seats`가 남는다. Python: 보고서 항목에 `runnable`과 `run_error`(`compile_flow`가
받는지)가 붙는다. 대시보드(`pages/flows/`, `lib/flowGraph.ts`, 카탈로그 `i18n/{ko,en}/flows.ts`): `@xyflow/react`
12.12.0 고정(`--ignore-scripts`로 설치). 설계와 다른 점:

- **템플릿 편집기는 없앴다.** "흐름 종류" 탭은 흐름(저장된 흐름, 변환된 템플릿과 팀)을 나열하고 흐름만 편집한다(D7).
  `TemplatesTab`, `TemplateDialog`, `flowTemplateEditor.ts`, `flowTemplates` 카탈로그와 그 테스트를 지웠다.
  `/api/flow-templates`와 CLI는 허브를 위해 남긴다.
- **편집기**는 넓은 대화상자다: 팔레트(맡은 일마다 버튼, 정리자, "자동 정렬"), 캔버스(끌어서 놓기, 손잡이를 다른 요소에
  끌어 연결, 앞으로 가는 연결의 순환을 만들 연결은 되돌아보기 연결이 됨, 마감에는 승인과 거부 손잡이), 고른 요소의
  패널(흐름, 자리, 동시 묶음, 마감, 연결). 동시 묶음 구성은 틀 안으로 끌어 넣는 대신 자리 패널에서 고르고, 구성원은
  묶음 안에 자동으로 놓인다. 기록과 초점은 아직 실행되지 않아 보여 주지 않는다. 클라이언트 검사가 흔한 문제를 요소에
  표시하고, 저장할 때 허브가 다시 검증한다. 기본 제공 흐름, 팀, 템플릿은 같은 id의 내 흐름으로 저장되어 그것을 가린다.
- **갤러리** 행은 작은 다이어그램 대신 모양을 글로(`작성 → 비평 ×2 → 정리 → 마감`), 자리 수와 호출 수, 이유와 함께
  "아직 실행할 수 없음"을 보여 준다.
- **시작 화면**: 흐름 선택기가 템플릿 선택기를 대신하고, 프로젝트 종류에 맞는(또는 `projects`가 없는) 유효하고 실행되는
  흐름만 보여 준다. 자기 과제 문안이 있는 흐름은 매개변수(D8 종류)를, 없는 흐름은 과제를 묻는다. 팀 선택은 과제를
  직접 쓸 때만 보인다. 자리별 캐릭터는 접힌 영역에서 그 자리의 일로 걸러 바꿀 수 있다.
- **보기 화면**: 토론 결과의 "흐름" 접힘 영역을 열면 흐름을 읽기 전용으로 그린다(실행된 자리는 초록, 대체 답은 실패,
  실행 뒤 흐름이 바뀌었으면 안내). Agents 모니터는 바꾸지 않았다.
- **좁은 화면**에서는 캔버스 대신 자리와 연결 목록과 패널을 보여 준다.
- **용어집**: 흐름, 자리, 맡은 일, 동시 묶음, 마감, 연결, 받는 방식, 정리자를 `docs/glossary.ko.md`(두 언어)에 더했다.
- **실제 브라우저 확인(2026-11-01, 이 트리로 빌드한 로컬 허브와 임시 데이터 디렉터리).** 갤러리가 기본 제공 팀을 모두
  흐름으로 보여 줬다. `cross-review`에서: 다이어그램, 정리자 추가, 끌어서 비평가 -> 정리자 -> 마감 연결, 마감을 요약으로,
  저장(팀을 가리는 내 흐름, D4 경고). 시작 화면은 과제 칸과 자리별 캐릭터 선택과 함께 그 흐름을 보여 줬다. 찾아서 고친
  것: 새 자리가 시작 위에 겹쳐 그려짐(xyflow 크기 측정이 옛 위치를 되써 넣음), 접힌 채로 보기 화면을 맞춤. 흐름으로 시작한
  시험 토론이 Mac에 설치된 `claude`를 불러(팀이 제공자를 지정) 약 20초 뒤 취소했다. 확인하지 못한 것: 끝난 실행의 보기
  화면.
- **열린 점:** 프로젝트의 `"team"` 키는 아직 저장된 흐름이 아니라 팀을 가리킨다. Agents 모니터의 그래프.
