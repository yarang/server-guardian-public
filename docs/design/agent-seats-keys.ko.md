# 에이전트 자리와 API 키 지정: 사용자가 정하고, 키는 허브가 보관 (설계)

[English](agent-seats-keys.md) | 한국어

상태: 2026-10-29 제안. 범위와 키 보관 방식은 같은 날 운영자가 정했다 ("결정" 절). 아직 만들지 않았다 (K1-K4 단계).
출발: "에이전트의 역할과 API 키 할당은 사용자가 설정할 수 있도록 하자."

## 문제

- 토론 자리에 어떤 제공자(그리고 어떤 키)가 앉는지는 팀 파일에 손으로 적는다 (`"providers": ["zai"]`,
  `docs/design/debate-teams.ko.md`). 대시보드 팀 편집기는 목록만 보여 줄 뿐, 그 제공자가 준비됐는지, 자격 증명이
  어디서 오는지, 팀이 어떤 키에 기대는지는 알 수 없다.
- 키는 호스트마다 하나씩 있는 `llm.env` 파일에 있고, 파일 전체를 덮어쓰는 `scripts/deploy-llm-env.sh`로 채운다.
  키를 더하거나 바꾸려면 로컬 파일을 손으로 고쳐 다시 배포해야 하고, 키가 있는지, 어느 자리가 쓰는지,
  언제 정했는지는 대시보드 어디에도 없다.
- 호스트마다 제공자당 키가 하나다. 두 팀이 같은 제공자의 서로 다른 키를 쓸 수 없다.

## 범위

범위 안: 팀의 **토론 자리**, 곧 `expert`, `proposers`, `critic`, `judge`와 pipeline·versus 흐름의 `stages`, `sides`.
자리마다 사용자가 제공자(지금 있음), **키**(새로), 그리고 엔진 변경으로서 모델("열린 점")을 정한다.

범위 밖:

- **코드 편집 에이전트** (`scripts/zai-agent.sh`): `CLAUDE.md`의 작업 규칙으로 남고, 키는 운영자 기기에 둔다.
- 페르소나 문구와 이름(페르소나 편집기), 흐름의 모양 (`docs/design/flow-templates.ko.md`).
- CLI **로그인** (다음 절).

## 자격 증명 두 종류

| 종류 | 예 | 대시보드에서 설정 | 있는 곳 |
| --- | --- | --- | --- |
| 키 (환경 변수) | `ZAI_API_KEY`, `OPENAI_API_KEY`, `CLAUDE_CODE_OAUTH_TOKEN` | 가능 | 허브 키 저장소. 워커는 K3부터 작업마다 받는다 |
| CLI 로그인 | `~/.claude/.credentials.json`, `~/.codex/auth.json` | 불가, 절대 | 로그인한 호스트. 복사하지 않고 허브도 읽지 않는다 (`CLAUDE.md` "깨지 말아야 할 규칙") |

화면은 호스트의 제공자마다 출처를 하나 보인다: **허브 키**, **호스트 로그인**, **없음**. `zai`에는 로그인 출처가
없다. 키가 없으면 `없음`이고, 실행은 claude 로그인을 빌리지 않고 실패한다 (`zai-provider.ko.md`).

## 키 저장소

데이터 디렉터리 밖의 파일: `~/.guardian/llm-keys.json`, 모드 600, 재정의는 `GUARDIAN_LLM_KEYS_FILE` (시험은
`GUARDIAN_LLM_ENV`처럼 이것으로 격리한다). 일부러 `llm.env` 옆에 둔다. 야간 백업은 `~/.guardian/data`와 fleet 파일 둘만
묶으므로(`docs/operations/backup-restore.ko.md`), `data/` 안에 두면 모든 압축 파일에 모든 키가 들어간다.
쓰기는 원자적(임시 파일, 모드 600, rename)이며 인벤토리와 같은 방식의 잠금을 건다.

항목:

```json
{
  "id": "zai-main",
  "provider": "zai",
  "env": "ZAI_API_KEY",
  "fingerprint": "9c1e0a7b",
  "base_url": "https://api.z.ai/api/anthropic",
  "default": true,
  "set": "2026-10-29T09:12:00Z",
  "rotated": "2026-10-29T09:12:00Z",
  "value": "..."
}
```

- `id`: `[a-z0-9-]{1,40}`, 팀이 가리키는 이름. `provider`는 알려진 제공자여야 하고, `env`는 `env_policy`가 그 제공자에게
  보이게 허락한 이름(`PROVIDER_PREFIXES`)이어야 한다. `AGENT_*`, `GUARDIAN_*`, `TYPESAFE_*`는 안 된다.
- `fingerprint`: `sha256("sg-key-v1\0" + value)`의 앞 16진수 8자. 두 키를 구분하고 교체가 반영됐는지 보이는 용도이며,
  값의 일부(끝 네 글자 등)는 절대 아니다.
- `base_url`: 선택, 주소를 가진 제공자(`zai`, `ollama`)만. 엔드포인트를 바꿀 수 있는 사람은 거기로 보내는 키를 읽을
  수 있으므로 주소도 키만큼 보호한다: https(또는 루프백)만, **바꾸려면 키를 다시 입력**해야 하고, 바꿀 때마다 옛 호스트와 새
  호스트 이름을 감사 기록에 남긴다.
- `default`: 제공자마다 최대 한 항목. 키를 고정하지 않은 모든 자리가 쓴다.
- `value`는 쓰기 전용이다. 어떤 엔드포인트, 이벤트, 보고서, 로그, 오류 메시지도 값을 돌려주지 않는다. API는 메타데이터와
  `used_by`(그 항목을 고정한 팀)만 돌려준다.

## 자리의 해석

자리는 지금처럼 순서 있는 제공자 목록을 가진다. 자리는 키도 고정할 수 있다: `"key": "<id>"` (K2).

실행기는 제공자마다 다음 순서로 자격 증명을 고른다.

1. 자리가 **이** 제공자에 고정한 항목. 고정한 항목이 없거나, 지워졌거나, 다른 제공자의 것이면 **시작을 거부**한다
   (저장할 때와 시작할 때 두 번 검증). 기본 키나 로그인으로 물러서지 않는다.
2. 저장소에서 그 제공자의 `default` 항목.
3. 허브 `llm.env`의 같은 이름 값 (옛 방식, K4까지).
4. 호스트의 CLI 로그인 (`claude`, `codex`, `agy`). `zai`는 절대 아니다.

고정은 자기 제공자에만 적용하고, 체인의 다른 제공자는 2-4로 해석한다. 제공자 사이의 실패 대체는 그대로다. 둘 다 같은 이름을
정의하면 저장소가 `llm.env`를 이긴다. 화면이 보이는 것이 저장소이기 때문이다. `deploy-llm-env.sh`는 계속 `llm.env`만
덮어쓰고, 대시보드가 관리하는 것은 건드리지 않는다.

**이전:** `guardian.py --keys-import`가 허브 `llm.env`를 한 번 읽어 알려진 제공자 변수마다 항목 하나(`imported-<이름>`,
기본 키 표시)를 만든다. 아무것도 지우지 않는다. `llm.env`의 줄은 K4에서 운영자 OK를 받고 지운다.

## 전달

- **허브.** `LLMRunner`는 호출마다 `os.environ`, `llm.env`, 저장소로 환경을 만든 뒤 지금처럼
  `env_policy.provider_env`를 적용하므로, 제공자는 자기 접두사만 본다. 고정한 키에는 호출 단위 덮어쓰기
  (`run_session_prompt(..., key_env=...)`)가 필요하다. 설정이 아니라 **엔진 변경**이다.
- **워커** (K3, protocol 3). 허브가 항목의 환경 변수를 `run`의 stdin 본문에 실어 보내고, 워커는 이를 CLI 자식 프로세스의
  stdin으로 넘기며(`worker.py`의 `communicate(payload)`) 메모리에만 둔다. 작업 디렉터리, 호출 기록(`calls.jsonl`), `argv`,
  어떤 응답에도 쓰면 안 된다. 시험은 표지용 가짜 키를 심고 작업 뒤에 워커 디렉터리 전체를 검색한다. protocol 2에 머문 워커는
  K4까지 호스트 `llm.env`를 쓰며, 프로브가 protocol을 보고한다 (`probe-worker.sh`).
- 대시보드에서 CLI까지의 경로는 이미 비밀에 안전하다. `configSave`는 요청 본문을 Python CLI의 **stdin**으로 넘기고
  (`runConfigCLI(body, ...)`) `argv`에는 싣지 않으므로 `ps`에 보이지 않는다. 키 경로는 감사 줄(`source=keys`, id, 제공자,
  동작, 행위자, 값 없음)을 더하고 요청 본문 기록 대상에서 뺀다.

## API

팀과 같다: Go는 중계, 검증은 Python.

- `GET /api/keys` -> `{keys:[{id, provider, env, fingerprint, base_url, default, set, rotated, used_by:[팀 id]}],
  providers:[{id, installed, source: "hub key" | "host login" | "missing", ready, key}]}` (`--keys --json`)
- `POST /api/keys` (`--key-save`): 만들기 또는 교체. `value`는 만들 때, 교체할 때, `base_url`이 바뀔 때 필수이고, 없으면
  `default`만 바꿀 수 있다. 응답은 메타데이터만.
- `DELETE /api/keys/{id}` (`--key-delete`): 팀이 고정한 동안은 팀 id와 함께 `409`.
- 팀 파일: `members[].key`는 선택이며 id로만 참조한다. `validate_lineup`이 항목이 있는지, 구성원의 제공자 목록에 항목의
  제공자가 있는지 검사한다. 모르는 키는 저장할 때 오류.
- 이벤트: `agent_started.key`는 id를 싣는다 (값이나 다른 항목의 지문은 싣지 않는다).

## 대시보드

- **설정 > 키** (`#/settings/keys`): 항목 목록(제공자, 환경 변수 이름, 지문, `기본` 칩, 정한·교체 시각, 쓰는 팀)과 제공자별
  출처 칩 표. "키 설정 / 교체"는 비밀번호 입력란(`autocomplete="new-password"`)이 있는 양식을 열며, 미리 채우지 않고 제출하면 비운다.
- **팀 편집기**: 자리 행마다 제공자, 모델(K2b가 있을 때), 그 제공자 항목만 담은 키 선택기를 둔다. 비워 두면 "제공자의 기본 키"라고
  읽힌다. 팀마다 읽기 전용 **자리 표**(자리 -> 제공자 -> 모델 -> 키)를 편집기 위와 프로젝트의 팀 선택기에 보인다.
- 값은 `localStorage`, 초안, `debatePrefill`, `RerunInputs`, URL, 이벤트, 보고서 어디에도 두지 않는다.
  문자열은 새 `keys` 그룹으로 두 카탈로그(`ko`, `en`)에 함께 넣는다.

## 용어 (운영자 확인 전까지 제안)

`자리`(seat), `키`(키 저장소의 항목), `로그인`(CLI의 호스트 로그인), `기본 키`(default 항목). 기존 용어(팀, 페르소나,
제공자, 판정자)는 그대로다.

## 단계

- **K1** 키 저장소, 쓰기 전용 API, 설정 > 키. 허브만. `--keys-import`. 해석 2-4단계 (자리 고정 없음).
- **K2** 팀 파일의 자리 `key`, 검증, 편집기, 실행기의 `key_env`. **K2b** (선택, 별도 결정) 자리 `model`.
- **K3** 워커에 작업마다 전달 (protocol 3), 워커 6대 재프로브, 표지 키 시험.
- **K4** 호스트와 허브의 `llm.env`에서 키 제거. 운영자 OK 필요.

단계마다 `scripts/ci.sh`와 배포 사슬을 거친다. K1-K2는 Python, Go, 대시보드를, K3는 워커와 설치기를 건드린다.

## 결정

1. **범위: 토론 자리만** (운영자, 2026-10-29). 코드 편집 에이전트는 `CLAUDE.md`의 규칙으로 남는다.
2. **키는 허브가 보관하고 쓰기 전용** (운영자, 2026-10-29). *[zai-provider.ko.md](zai-provider.ko.md)의 결정 3("키를 허브뿐
   아니라 Tier-1 워커 호스트에도 배포한다")과 `worker.py`의 계약("그 호스트의 제공자 로그인을 쓴다")을 개정한다. K3부터 허브가
   작업마다 키를 넘기고, K4부터 호스트에는 키가 남지 않는다.* 그때까지 두 방식 모두 동작한다.
3. **CLI 로그인은 그 호스트에 남고** 대시보드가 설정, 표시, 복사하지 않는다.
4. 쓸 수 없는 고정 키는 시작을 거부하며, 다른 자격 증명으로 물러서지 않는다.

## 열린 점

- 자리별 모델. 지금 `llm_runner`에는 호출 단위 모델이 없다. zai 등급은 전역(`ZAI_{OPUS,SONNET,HAIKU}_MODEL`)이고 다른 CLI는
  자기 모델을 고른다. 자리 `model`은 엔진 변경이라 별도 결정이 필요하다 (K2b).
- "키 시험" 버튼(그 키로 PONG 한 번)과 공유 Codex 한도에 미치는 비용.
- 누가 키를 설정하는가: API 토큰이 하나(`AGENT_TOKEN`)라 토큰을 가진 누구나 키를 바꿀 수 있다. 별도 역할은 그 자체로 보안 변경이다.
- 모드 600과 샌드박스 외의 저장 시 암호화는 없다. 지금의 `llm.env`와 같다.
- 한 자리에 한 제공자의 키 여러 개(429에서 돌려 쓰기): 계획 없음. z.ai 429의 재시도 시간은 측정하지 않았다.
