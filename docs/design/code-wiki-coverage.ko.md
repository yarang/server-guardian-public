# 코드 위키의 범위 확장: 설계 문서 연결, 큰 범위 나누기, 파일 보기 (초안)

[English](code-wiki-coverage.md) | 한국어

상태: 초안(2026-10-13). A, B, C 모두 구현됨(아래 "구현 메모 (A)", "(B)", "(C)"), 2026-10-13에 C → A → B 순서로 넣었다. 결정이 필요했던 항목은 끝의 "열린 결정"에 모았다(모두 정해졌다).
바탕 설계: `debate-code-index-wiki.md`의 "2층. 코드 위키". 이 문서는 그 위에 더하는 변경만 적는다.
근거·탐색·인용 검증 규칙(위키는 길잡이이고 근거가 아니다)은 바꾸지 않는다.

## 문제

2026-10-13 허브에 만들어진 페이지는 `cli-llm-agent` 하나다. 같은 날 측정한 값:

1. **한 페이지가 다루는 범위가 너무 크다.** `cli/llm-agent/`는 테스트를 뺀 소스 38개(debate_engine.py 하나가 117KB)인데,
   페이지는 13.7KB이고 실제로 읽은 파일(`basis`)은 8개 남짓이다. 세션 하나와 6000자 안팎이라는 본문 목표로는
   큰 디렉터리를 다 다룰 수 없다. 기본 집합 규칙은 최상위 아래 한 단계까지만 나눈다(`wiki_build.default_candidates`).
   `apps/web-desktop/`은 소스 124개, 746KB가 한 페이지 범위다.
2. **설계 의도가 위키에 없다.** 바탕 설계가 풀려던 문제 5("왜 이렇게 되어 있나")의 답은 `docs/design/*.md` 13개의
   결정과 구현 메모에 이미 있다. 그런데 쓰기 프롬프트는 "코드를 인용하라"이고, 기본 집합은 코드 디렉터리만 고른다.
   `feature:` 페이지는 "사람이 만든다"고만 정해 두어 실제로는 하나도 없다.
3. **파일 단위로 볼 곳이 없다.** 파일 하나의 개요·정의·참조처는 1층 인덱스가 정확히 알고 있지만, 사람이 대시보드에서
   볼 방법이 없다. 위키 본문의 인용 칩도 누를 곳이 없다(대시보드는 저장소 웹 주소를 모른다).

측정: 설계 문서 13개는 모두 저장소의 코드 파일을 2개 이상 경로로 언급한다(전체 경로나 저장소에서 이름이 하나뿐인
파일 이름). 이 언급만으로 덮이는 코드 파일은 `cli/llm-agent` 38개 중 22개, `apps/agent` 22개 중 10개,
`apps/web-desktop` 124개 중 6개, `packages/guardian-ui` 33개 중 0개다.
설계 문서만으로 페이지를 나눌 수는 없고(2), 크기 기준 나누기(3)가 따로 필요하다는 뜻이다.

## 결정 요약

| 번호 | 변경 | LLM 비용 | 바뀌는 것 |
|---|---|---|---|
| A | 설계 문서마다 기능 페이지(`feature-<문서 이름>`) | 문서당 세션 1개 | 기본 집합, 쓰기 프롬프트, 페이지 메타(`kind`, `docs`) |
| B | 기준을 넘는 디렉터리 범위를 묶음 페이지로 나누고, 원래 디렉터리 페이지는 개요 페이지로 | 묶음당 세션 1개 | 기본 집합, 쓰기 순서, 개요 프롬프트 |
| C | 파일 보기(LLM 없음): 개요, 정의, 들어오는 참조, 이 파일을 다루는 페이지와 문서 | 없음 | 새 읽기 명령과 API, 대시보드 화면, 인용 칩 링크 |

세 변경 모두 페이지 저장 형식(front matter)은 하위 호환으로 넓히고, 기존 페이지는 그대로 읽힌다.
`WIKI_PROMPT_VERSION`이 오르므로 기존 LLM 페이지는 `--stale` 대상이 된다(사람 페이지는 그대로).

## 페이지 종류

front matter에 `kind`를 더한다. 없으면 `dir`로 읽는다(지금 페이지 전부).

| kind | id | scope | 누가 만드나 |
|---|---|---|---|
| `dir` | `cli-llm-agent` (지금과 같음) | 디렉터리 1개 | 기본 집합. 기준 이하 디렉터리 |
| `overview` | `cli-llm-agent` (같은 id 유지) | 디렉터리 1개 | 기본 집합. 기준을 넘어 나뉜 디렉터리 |
| `group` | `cli-llm-agent--<묶음 이름>` | 파일 목록 | 기본 집합(B) |
| `feature` | `feature-<문서 파일 이름>` | 설계 문서 1개 + 그 문서가 언급한 코드 파일 | 기본 집합(A), 사람 |

- id 규칙(`^[a-z0-9][a-z0-9-]{0,63}$`)은 그대로다. `--`는 이미 허용되는 문자열이다.
- `scope` 항목 상한 `MAX_SCOPE_ENTRIES`를 20에서 60으로 올린다. `debate-code-index-wiki.md` 하나가 코드 파일 41개를 언급한다.
- 개요 페이지가 디렉터리 페이지와 같은 id를 쓰므로, 지금 `[[cli-llm-agent]]` 링크와 대시보드 주소는 깨지지 않는다.

## A. 설계 문서와 기능 페이지

### 문서 찾기

- 프로젝트 설정(`configs/projects/<id>.json`, 대시보드 등록 프로젝트도 같은 형식)에 선택 필드 `wiki.docs`(글롭 목록)를 둔다.
  없으면 기본값 `["docs/design/*.md", "docs/adr/*.md", "docs/architecture/*.md", "ARCHITECTURE.md", "DESIGN.md"]`.
- 읽을 수 있는 파일(`RepoTools.readable`)만, 1MB 이하만 쓴다. 비밀 패턴 제외 규칙은 그대로 적용된다.
- 문서가 코드 파일을 2개 미만 언급하면 기능 페이지를 만들지 않는다(연결할 코드가 없다). 대신 C의 "이 파일을 언급한 문서"에는 나온다.

### 문서와 코드 연결 (결정적)

- 문서 본문에서 `RepoTools.cited_locations`와 같은 토큰 규칙으로 저장소 파일 언급을 찾는다. 전체 경로와,
  저장소에서 이름이 하나뿐인 파일 이름(`wiki_build.py`)을 모두 센다. 이름이 겹치면 세지 않는다.
- 기능 페이지의 `scope` = `[문서 경로] + 언급된 코드 파일(문서에 처음 나온 순서, 59개까지)`. 디렉터리는 넣지 않는다.
  디렉터리를 넣으면 그 안의 새 파일마다 `stale`이 되는데, 그 파일은 문서와 상관없을 수 있다.
- `.md` 같은 다른 문서 언급은 `scope`에 넣지 않고 front matter `docs`에 적는다(관련 문서 표시용).

### 쓰기 프롬프트 (feature)

일반 프롬프트와 같은 탐색 규약을 쓰고, 과제와 답 형식만 다르다.

- 섹션: `## 설계 의도`, `## 구현 위치`, `## 설계와 다른 점`, `## 주의점`, `## 관련 페이지` (영어는 `Intent`, `Where it lives`, `Drift`, `Caveats`, `Related pages`).
- **인용 규칙:** 설계 의도와 결정은 문서 줄(`docs/design/x.md:120-128`)을, 동작에 관한 주장은 코드 줄을 인용한다.
  문서 인용으로 동작을 주장하지 않는다. 문서와 코드가 다르면 `설계와 다른 점`에 두 인용을 함께 적는다.
  문서가 "구현 메모"에 이미 적은 차이는 그대로 옮기지 말고, 지금 코드에서 여전히 맞는지 확인한 것만 적는다.
- 문서 인용도 지금의 줄 단위 인용 검증을 그대로 거친다(문서도 저장소 파일이다). 한 번 되묻기 규칙도 같다.
- 문서가 길면(48KB 넘음) 첫 프롬프트에는 문서의 제목 목록(h2/h3와 줄 번호)만 주고, 필요한 절을 `read`로 읽게 한다.

### 낡음

- 문서 파일이 `basis`에 들어가므로 문서가 고쳐지면 페이지가 `stale`이 된다. 코드가 바뀌어도 지금처럼 `stale`이다.
- `scope`가 파일 목록이라 "범위 안의 새 파일" 검사는 사실상 없다. 대신 문서가 새 파일을 언급하게 되면 문서가 바뀐 것이므로 `stale`이다.
- 문서가 지워지면 `removed`로 `stale`, 다음 `--stale`에서 다시 쓰지 않고 건너뛰며 이유 `doc_removed`를 남긴다(페이지 삭제는 사람이 한다).

### 기타 문서 (README, 운영 문서, 평가 보고서)

별도 페이지를 만들지 않는다. C의 파일 보기와 개요 페이지 프롬프트에 "이 범위의 파일을 언급한 문서" 목록(경로와 제목 한 줄)으로만 들어간다.
이유: 운영 절차와 평가 결과는 설계 의도보다 빨리 낡고, 코드와의 대응이 약하다. 필요하면 사람이 `feature-` 페이지를 직접 만든다.

## B. 큰 범위 나누기

### 기준

디렉터리 후보(지금의 `default_candidates` 결과)마다 코드 파일 수와 바이트를 센다(테스트·미리보기 제외, 지금 규칙).
`files > 15` 또는 `bytes > 200KB`이면 나눈다. 두 값은 `GUARDIAN_CODE_WIKI_SPLIT_FILES`, `GUARDIAN_CODE_WIKI_SPLIT_BYTES`로 바꿀 수 있다.

측정(2026-10-13): `cli/llm-agent` 38개·774KB, `apps/web-desktop` 124개·746KB, `apps/agent` 22개·264KB가 나뉜다.
`scripts` 13개·113KB, `packages/guardian-ui` 33개·65KB는 파일 수 기준으로 `guardian-ui`만 나뉜다.

### 묶는 방법 (결정적, LLM 없음)

1. **하위 디렉터리가 있으면 먼저 하위 디렉터리로 나눈다** (`apps/web-desktop/src/pages/`, `src/lib/` …). 나뉜 결과가 기준을 넘으면 그 안에서 다시 이 규칙을 적용한다(최대 깊이 4).
2. **평평한 디렉터리(또는 나눈 뒤 남은 직속 파일)는 참조 그래프로 묶는다.**
   - 간선: 파일 A가 파일 B에서만 선언된 이름을 참조하면 A→B(1층 인덱스의 선언 표와 식별자 출현. 이름이 여러 파일에 선언됐으면 세지 않는다).
   - 허브 파일 제외: 같은 디렉터리 파일의 1/3 이상이 참조하는 파일(예상: `repo_tools.py`, `debate_engine.py`)은 간선 계산에서 빼고, 가장 많이 참조하는 묶음에 넣는다.
   - 남은 그래프의 연결 요소가 묶음이다. 묶음이 기준을 넘으면 파일 이름 순으로 기준 안에 들게 자르고, 파일 2개 미만인 묶음은 "기타" 묶음으로 모은다.
   - 묶음 이름: 묶음 안에서 같은 디렉터리 파일에게 가장 많이 참조되는 파일의 이름(확장자 뺌). 예: `cli-llm-agent--code-wiki`.
3. **이미 기능 페이지(A)가 다루는 파일도 묶음에서 빼지 않는다.** 기능 페이지는 설계 관점, 묶음 페이지는 코드 관점이라 겹쳐도 된다. 대신 묶음 프롬프트에 "이 파일을 다루는 기능 페이지" id를 주고 링크하게 한다.

묶음은 sha마다 다시 계산하지 않는다. 처음 만들 때 정한 `scope`(파일 목록)를 페이지에 저장하고, 그 뒤로는 지금처럼 낡음으로 다룬다.
범위 안에 새 파일이 생기면 그 파일이 어느 묶음에도 없다는 사실이 개요 페이지의 `stale` 이유("묶음이 다루지 않는 새 파일")가 된다.
다시 나누기는 `--code-wiki-build --regroup DIR`(사람이 고르는 명시적 작업)으로만 한다. 기존 묶음 페이지 중 파일이 모두 빠진 것은 지우지 않고 `broken`으로 남겨 사람이 정리한다.

`--dry-run`이 LLM 없이 제안 묶음(id, 파일, 바이트, 허브 파일)을 보여 준다. 처음에는 이것을 보고 기준을 조정한다.

### 개요 페이지

- 나뉜 디렉터리의 원래 id 페이지는 `kind: overview`가 된다. 묶음 페이지를 모두 쓴 뒤에 쓴다(한 빌드 안에서 순서를 정한다).
- 프롬프트에 하위 페이지의 id·제목·`## 역할` 첫 문단을 주고, 디렉터리 전체의 역할과 "무엇을 보려면 어느 페이지"를 쓰게 한다. 섹션은 지금과 같다(`역할`, `흐름`, `주의점`, `관련 페이지`).
- 하위 페이지 서술은 근거가 아니므로 개요도 주장마다 코드를 인용한다(지금 규칙 그대로). 개요는 읽을 코드가 적으므로(진입점 위주) 세션이 짧다.
- 개요 `basis`에는 하위 페이지를 넣지 않는다. 하위 페이지가 다시 쓰여도 개요는 `stale`이 되지 않는다(관련 링크만 맞으면 된다).

### 첫 프롬프트와 상한

- 기본 페이지 상한 `MAX_DEFAULT_PAGES` 20을 80으로 올린다(이 저장소 예상: 기능 13 + 묶음 약 30 + 개요·디렉터리 7).
- 토론 첫 프롬프트의 위키 목록(최대 40줄)은 `overview`·`dir`을 먼저, 그 다음 `feature`, 마지막 `group` 순서로 넣는다. 넘치면 `... N more fresh pages`(지금과 같음).
- 한 빌드의 세션 수가 많아지므로 `--all`이나 첫 기본 빌드는 대시보드에서 확인창에 세션 수를 보여 준다. 한 번에 다 돌리지 않고 `--page`나 `--kind feature`로 나눠 돌릴 수 있게 `--kind` 선택을 더한다.

## C. 파일 보기 (LLM 없음)

### 읽기 명령과 API

`wiki_ops.py`에 `--code-file-show PATH --project P [--sha S]`를 더한다(2026-10-18: 구현은 `file_view.py`이고 `guardian.py`가 부른다. 경로는 쿼리 `?path=`로 받는다. 아래 "구현 메모 (C)"). 출력:

```
{"ok", "project", "sha", "path", "language", "size",
 "outline": [{"name", "kind", "start", "end", "signature"}],
 "incoming": [{"path", "count"}],          // 이 파일의 선언을 참조하는 다른 파일(1층, Go는 타입 정보)
 "outgoing": [{"path", "count"}],          // 이 파일이 참조하는 다른 파일
 "pages": [{"id", "kind", "title", "state", "via": "scope" | "basis" | "cited"}],
 "docs": [{"path", "title", "lines": [N]}] // 이 파일을 언급한 문서(A의 연결 규칙)
}
```

- `--code-file-read PATH --start N --end M`은 원문 줄을 준다(최대 400줄, 64KB). 읽을 수 없는 파일(비밀·심볼릭 링크·바이너리)은 오류.
- Go API: `GET /api/projects/{id}/files/{path...}?sha=` → show, `GET .../files/{path...}/lines?start=&end=&sha=` → read. 인증과 행위자 기록은 위키 경로와 같다.
  저장소 원문을 대시보드로 내보내는 첫 경로이므로, 응답은 `RepoTools.readable`을 통과한 파일만이고 감사 로그(`audit/exec.jsonl`과 같은 형식의 `files.jsonl`)에 경로와 줄 범위를 남긴다.

### 대시보드

- 위키 탭에 두 번째 목록 "파일"을 둔다(트리, 검색). 주소 `#/debates/wiki/file/<path>`. (2026-10-18: 구현한 주소는 `#/debates/wiki?file=<path>`와 `?view=files`다. 아래 "구현 메모 (C)".)
- 파일 화면: 개요(접을 수 있는 선언 목록), 들어오는/나가는 참조, 이 파일을 다루는 위키 페이지(상태 칩), 이 파일을 언급한 문서. 선언을 누르면 그 줄 범위의 원문을 아래에 보여 준다.

## 검증

- **결정성:** 같은 sha에서 기본 집합(기능 연결, 묶음)이 같은 바이트로 나온다(`--dry-run --json`을 두 번 비교).
- **이 저장소의 dry-run 기대값:** 기능 페이지 13개, 각 `scope`의 첫 항목이 문서 경로. `cli/llm-agent` 묶음에 `debate_engine.py`·`repo_tools.py`가 허브 파일로 표시된다. 결과를 이 문서의 "측정"에 덧붙인 뒤 구현 기본값을 확정한다.
- **미끼 검증:** 문서 줄만 인용해 동작을 주장한 기능 페이지 답("X는 Y를 한다 (`docs/design/a.md:10`)")은 코드 인용이 없으므로 프롬프트 규칙 위반이다. 이를 기계적으로 잡을 수는 없으므로, 평가 2차 질문 세트에 "설계와 다른 점" 질문을 하나 더해 사람이 판정한다.
- **낡음:** 문서만 고친 커밋에서 그 기능 페이지만 `stale`이 되고, 같은 파일을 다루는 묶음 페이지는 `fresh`로 남는다.
- **파일 보기:** 비밀 패턴 경로(`config/secrets/x.yaml`)의 show/read가 404로 거부되고, read 시도는 감사 로그에 `error`로 남는다. 칩 링크가 줄 범위를 연다.

## 하지 않는 것

- 파일마다 LLM 서술을 만들지 않는다. 파일 단위는 C의 기계 생성 보기로 충분하고, 낡음과 비용이 파일 수에 비례해 커진다.
- 설계 문서를 위키 페이지로 복사하지 않는다. 기능 페이지는 문서를 요약하고 인용할 뿐이고, 원문은 문서다.
- 결정 DB(토론 결과)를 위키에 넣지 않는다. 그것은 저장소 밖 허브 데이터이고 sha와 묶이지 않는다.
- 묶음을 커밋마다 자동으로 다시 나누지 않는다(페이지 id가 흔들린다).
