[English](agent-characters.md) | 한국어

상태: 2026-10-30 제안. "AI로 제안" 단계(2.6절)와 C0(가이드와 린트, 2026-10-31)을 구현·배포했고(2026-10-31, `670d6c7`, 실제 브라우저 확인), 코드 팀의 C1(역할 카드, 2026-10-31)은 구현·배포했고(2026-10-31, `6e0fb08`) 시험 토론을 한 번 돌렸다(2026-10-31, `guardian-dev`, 2라운드에서 승인). ops 팀의 C1(2026-10-31: 네 ops 팀 모든 페르소나의 역할 카드, 카드는 기본 자리를 따름, 운영자가 승인한 새 카드 문장, 프롬프트 p25)은 구현했고 ops 팀마다 시험 토론을 한 번 돌렸으며(2026-10-31: 넷 모두 1라운드에서 승인, 기준보다 나빠진 팀 없음, `fleet-provision`은 이제 읽기 전용 수집 계획을 씀) 배포했다(2026-10-31, `91fa7eb`). 나머지는 구현 없음. 출발점: 운영자가 페르소나 시스템 검토를 요청하며 "캐릭터와 같은 구조를 만들어 다양한
캐릭터를 사용하는 형태로 하고, 페르소나는 그 캐릭터의 정의가 된다. 너무 길지 않아야 하니 정형화를 위한 가이드도 필요하다"고
제안했다. 같은 날 추가: "프로필에 캐릭터의 사진을 만들어 넣을 수 있게 하고, 생성은 gemini나 codex로 하자"(2.4절, C5 단계).

## 1. 현재 페르소나 시스템 검토

지금의 페르소나(`cli/llm-agent/persona_manager.py`, `configs/personas/*.json`):

- 필드 `id`, `name`, `role`, `domain`, `system_prompt`(최대 20,000자), `focus_areas`, `critique_focus`,
  `mcp_capabilities`. 기본 제공은 `configs/personas`, 사용자 수정본은 `<GUARDIAN_DATA_DIR>/personas`.
- 모델에 닿는 것은 `system_prompt`뿐이다(`RolePrompt.persona`, `debate_engine.py:542`). `mcp_capabilities`는 판정자의
  도구를 좁힌다(`team_manager.py:judge_tools`). `domain`, `focus_areas`, `critique_focus`는 보여 주기만 하고 보내지 않는다.
- 자리(expert, proposer, critic, judge, stage, side)는 페르소나가 아니라 팀 파일이 정한다. 페르소나의 `role`은 자유 텍스트다.

기본 제공 페르소나 29개를 잰 결과(2026-10-30):

| 관찰 | 수 |
|---|---|
| `system_prompt` 길이 | 122 - 958자, 중앙값 약 500자 |
| 팀 자리 하나에서만 쓰이는 페르소나 | 팀이 쓰는 27개 중 24개(나머지 3개는 `default`/`cross-review` 짝) |
| 어느 팀에도 없는 페르소나 | 2개(`general_assistant`, `server_guardian`: CLI 대화 전용) |
| ops 인용 규칙 `[#번호 조회 호스트]`를 반복하는 페르소나 | 9개 |
| 코드 인용 규칙 `파일:줄`을 반복하는 페르소나 | 7개 |
| `[차단]`/`[권고]` 등급 문단을 반복하는 ops 비판자 | 7개(판정자 4개는 그 읽는 법을 반복) |
| "사용자가 시키지 않은 금지 조건을 만들지 마라"를 반복하는 판정자 | 4개 |

여기서 드러나는 문제:

1. **'누구'와 '어떻게'가 한 텍스트에 섞여 있다.** 페르소나 하나에 캐릭터(전문성, 관점)와 자리의 행동(등급 문단, "문제가
   없으면 없다고", "금지 조건을 만들지 마라"), 프로젝트 종류의 근거 형식(`파일:줄`, `[#번호 조회 호스트]`, ops 블록),
   프로젝트 사실(`guardian_lead_dev`가 저장소 제약을 되풀이)이 함께 들어 있다. 같은 규칙이 4-9벌 복사되어 있어, 2026-10-19
   `fleet-provision` 판정자 보정 같은 조정을 사본마다 손으로 해야 하고 사본은 서로 어긋난다.
2. **재사용이 없다.** 페르소나와 자리가 1:1이다. 안전 검토자는 세 벌(`ops_safety_critic`, `ops_service_safety_critic`,
   `ops_provision_safety_critic`)이며 주로 범위 문장만 다르다. 새 팀은 새 페르소나를 뜻한다.
3. **역할에 타입이 없다.** 단독 실행기는 id나 본문에서 `"judge"` / `"jev_mcp"`를 찾아 판정자를 거른다
   (`solo_agent.py:59`). 페르소나가 어떤 자리에 앉을 수 있는지 적는 곳이 없기 때문이다.
4. **죽은 필드가 잘못된 수정을 부른다.** `focus_areas`와 `critique_focus`는 에이전트를 이끄는 것처럼 보이지만 보내지지
   않는다(2026-10-30 `debate-teams.md`에 기록). 운영자가 고쳐도 아무것도 바뀌지 않는다.
5. **길이와 형식 규칙이 없다.** 상한은 20,000자뿐이다. 가장 긴 프롬프트가 긴 이유는 캐릭터 때문이 아니라 자리와 종류의
   규칙을 싣고 있어서다.

지켜야 할 장점: 지금 페르소나는 짧고(1,000자를 넘는 것이 없음), 모든 기본 제공 페르소나가 근거를 인용하며, 스스로 실행한다고
주장하는 것이 없고(`test_builtin_personas.py`), 사용자 수정본은 체크아웃을 건드리지 않으며, 판정자의 도구는 팀이 좁힐 수만 있다.

## 2. 제안: 캐릭터 = 페르소나 + 프로필, 자리·종류와 조합

**캐릭터**는 다시 쓰는 에이전트 정체다. 그 **페르소나**는 모델에 닿는 정의이고, **프로필**은 사람이 보는 부분이다. 자리,
근거 형식, 프로젝트에 관한 것은 더 이상 캐릭터에 두지 않고, 캐릭터가 자리에 앉을 때 엔진이 덧붙인다:

```
한 턴의 시스템 프롬프트 =
    character.persona        (누구: 정체, 전문 분야, 관점, 먼저 볼 것, 하지 않는 것)   <- 캐릭터 파일
  + 역할 카드                (이 자리에서 어떻게: critic, judge, ...)                 <- 엔진, 자리 x 종류별
  + 자리 초점(선택)          (이 팀이 이 캐릭터에게 바라는 것)                        <- 팀 파일
  + 종류 프로토콜            (근거 형식: repo 블록 / ops 블록 / 인용)                 <- 엔진(현재 있음)
  + 규칙                     (언어, 답 형식)                                          <- 엔진(현재 있음)
```

그래서 "안전 검토자"는 캐릭터 하나이고, `fleet-ops`, `fleet-services`, `fleet-provision`은 각자 한 줄짜리 자리 초점을 붙여
비판자로 앉힌다. `[차단]`/`[권고]` 등급은 ops 비판자 역할 카드에 한 번만 적는다.

### 2.1 캐릭터 파일

```json
{
  "id": "safety_reviewer",
  "format": 2,
  "name": "안전 검토자",
  "profile": {
    "tagline": "조치가 무엇을 지우고 멈추는지 실행 전에 안다",
    "look": "차분한 중년 엔지니어, 짧은 회색 머리, 형광 안전 조끼, 체크리스트를 든 모습"
  },
  "seats": ["critic", "verifier", "solo"],
  "kinds": ["ops"],
  "role_card": "critic",
  "role_card_kind": "ops",
  "persona": {
    "identity": "운영 변경이 잃게 하는 것을 실행 전에 드러내는 검토자",
    "expertise": ["되돌릴 수 없는 삭제와 데이터 손실", "감사·보안 기록 보존", "서비스 가용성"],
    "stance": "정리가 목적이다. 검토는 삭제와 중단을 의도한 것으로 만들기 위한 것이지 일을 막기 위한 것이 아니다.",
    "checks": ["조치마다 지우거나 멈추는 것", "대상 호스트와 sudo", "점검 결과와 다른 수치"],
    "boundaries": ["보관 정책과 재발 방지는 다른 검토자의 일", "새 전제(점검 창, 백업)를 요구하지 않는다"]
  }
}
```

- 보내는 것은 `persona`뿐이다. 엔진은 고정된 틀(2.5) 하나로 렌더링하므로 모든 캐릭터가 같은 모양으로 읽히고, 필드 밖에
  엉뚱한 지시를 끼워 넣을 수 없다.
- `profile`은 보여 주기만 한다(대시보드 명단, 이벤트 카드). 캐릭터의 개성(아바타, 색, 한 줄 소개, `look`, `portrait`)은
  여기에 두며 토큰과 편향을 늘리지 않는다. 아이콘과 색은 초상이 없을 때의 대체로 남는다(2.4절). C2는 `tagline`과
  `look`만 받고, `avatar`, `color`, `portrait`는 C4/C5에서 들어온다.
- `seats`는 자유 텍스트 `role`을 대신한다. 이 캐릭터가 앉을 수 있는 자리(`expert`, `proposer`, `critic`, `verifier`,
  `judge`, `stage`, `side`, `solo`). 팀 검증은 다른 자리를 거부하고, 단독 실행기는 id 대신 이것을 읽는다.
- `kinds`(선택): 이 캐릭터가 대상으로 쓰인 프로젝트 종류(`code`, `ops`, `design`). 비면 모두.
- `role_card`와 `role_card_kind`: 엔진 카드가 따라가는 본래 자리와 그 카드의 종류(C1, 2026-10-31 운영자 결정).
  `seats`에 expert, critic, judge가 있으면 필수이고, `role_card`는 `seats` 중 하나, `role_card_kind`는 `kinds`가
  있으면 그중 하나여야 한다.
- `tools`(선택): 판정자 자리에서만 쓰는, 제안할 수 있는 도구의 상한(지금의 `mcp_capabilities`). 카탈로그 전체를
  쓰려면 키를 빼고, 빈 목록은 "전부"로도 "없음"으로도 읽힐 수 있으므로 거부한다.
- `domain`, `focus_areas`, `critique_focus`는 없앤다. 그 내용은 보내지는 `expertise`와 `checks`로 옮긴다.

### 2.2 팀 자리 초점

팀의 자리는 `"focus": "<한 문장, 200자 이하>"`를 더할 수 있고, 역할 카드 뒤에 렌더링된다. 재사용하는 캐릭터를 팀에 맞게
만드는 부분이다("이번 정리의 안전만 본다. 재발은 용량 검토자의 일").

### 2.4 초상(생성한 사진)

캐릭터는 초상을 가질 수 있다. 명단 카드, 편집기, 이벤트 카드의 자리 옆에 보이는 정사각형 그림이다. 사람이 요청할 때
이미지 모델이 만들며, 토론 중에는 만들지 않고 에이전트에게 보내지도 않는다.

**누가 만드나.** 사람이 요청마다 생성기를 고른다:

| 생성기 | 경로 | 자격 증명 | 상태 |
|---|---|---|---|
| `gemini` | HTTPS로 Gemini API 이미지 모델 호출(`urllib`, 표준 라이브러리), 모델 id는 `GUARDIAN_PORTRAIT_GEMINI_MODEL` | `GEMINI_API_KEY`: K1이 생기면 `agent-seats-keys.md`의 키 저장소, 그 전에는 허브의 `llm.env` | CP0에서 확인 |
| `codex` | 버리는 임시 디렉터리에서 `codex exec`, `image_generation`만 켜고 나머지 도구는 모두 끔(토론 실행에서는 계속 꺼 둠) | 허브의 codex 로그인(운영 토론과 할당량 공유) | 도구는 있다(`imagegen`, `debate-agent-retrieval.md`). 파일을 어디에 어떤 형식으로 쓰는지는 CP0에서 확인 |

`agy`(CLI를 통한 Gemini)는 이미지 생성이 공식 문서로 확인될 때까지 경로가 아니다(`design-project.md`에 미확인으로
적혀 있다). CP0을 통과하지 못한 생성기는 대시보드에 나오지 않는다.

**프롬프트.** 이미지 프롬프트는 허브가 만들고 사람은 `look`(200자 이하)만 쓴다. 고정 부분: 하우스 스타일(모든 캐릭터에 한
스타일, 명단이 한 세트로 보이도록), 정사각형, 머리와 어깨, 단색 배경, 글자 없음, 가상의 인물. `name`, `tagline`, 페르소나는
보내지 않고 `look`만 보낸다. `look` 규칙(저장할 때 검사): 실존 인물이나 공인 금지, 브랜드·로고·기존 창작 캐릭터 금지,
그림에 그릴 글자 금지.

**후보.** 요청 한 번에 후보 1-4개(기본 2개)를 임시 디렉터리에 만들고, 사람이 하나를 고르거나 고르지 않는다. 고르지 않은
후보는 24시간 뒤 지운다. 생성은 자기 슬롯(`GUARDIAN_MAX_PORTRAITS`, 기본 1)에서 제한 시간을 두고 돌며, 감사 기록(행위자,
캐릭터 id, 생성기, sha256. 다른 필드의 프롬프트 텍스트는 없음)을 남긴다.

**저장과 제공.**

- 사용자 캐릭터: `<GUARDIAN_DATA_DIR>/character-portraits/<id>/<sha256>.<확장자>`, 바꾸지 않는 파일. 캐릭터 파일은 파일
  이름을 가리킨다. 초상을 바꾸면 새 파일을 쓰고, 어느 캐릭터도 가리키지 않는 옛 파일은 지운다. 야간 백업에 포함한다(작은 파일).
- 기본 제공 캐릭터: 운영자가 그림을 승인한 뒤에만 `configs/personas/portraits/`에 커밋한다. 그 전에는 아이콘과 색을 보인다.
- **크기: 256x256으로 저장**(2026-10-30, 운영자가 1024는 너무 크다고 봐서 결정). 그림은 이벤트 카드에서 24-32 CSS px,
  명단 카드에서 64-96 px, 편집기에서 128 px로 보인다. 256이면 가장 큰 표시를 2배 화소 밀도로 덮고, 흔한 프로필 크기도 같은
  범위다(아바타는 보통 80-512 px 사이로 제공된다). 생성기는 1024x1024 안팎으로 답하므로 후보는 임시 디렉터리에 원본 크기로
  두고, **고른 그림을 대시보드가 브라우저에서 줄여**(canvas, WebP, WebP 인코딩이 없으면 PNG) 보낸다. 엔진은 표준
  라이브러리만 쓰므로 크기를 바꿀 이미지 라이브러리가 없다. 올린 그림도 같은 방식으로 줄인다.
- 허브는 WebP나 PNG만 받는다. 매직 바이트로 확인하고, 정확히 256x256(WebP/PNG 헤더는 표준 라이브러리로 읽음, 재인코딩
  없음), 256 KiB 이하(256x256 WebP는 보통 10-40 KiB). 그 밖은 변환하지 않고 거부한다.
- `GET /api/personas/{id}/portrait`: 읽을 때마다 sha256 확인, 확장자의 고정 콘텐츠 형식, `X-Content-Type-Options: nosniff`,
  산출물 API와 같은 샌드박스 CSP. 대시보드는 `<img>`로만 보인다.
- 생성 대신 사람이 그림을 올릴 수도 있다. 같은 검사를 거친다.

**API.** `POST /api/personas/{id}/portrait/generate` `{generator, look, count}` -> 작업 id;
`GET /api/personas/{id}/portrait/jobs/{job}` -> 상태와 후보 URL; `POST /api/personas/{id}/portrait` `{job, candidate}` 또는
업로드 -> 초상 지정; `DELETE /api/personas/{id}/portrait` -> 아이콘과 색으로 되돌림. CLI: `guardian.py --portrait-generate <id>
--generator gemini|codex`, `--portrait-prune`.

### 2.5 렌더링(고정 틀)

```
당신은 {identity}입니다.
전문 분야: {expertise, 쉼표로}.
관점: {stance}
먼저 확인할 것:
- {checks...}
당신의 일이 아닌 것:
- {boundaries...}
```

틀은 프롬프트 언어로 쓴다(지금은 한국어). 프롬프트의 일부이므로 바꾸면 `RETRIEVAL_PROMPT_VERSION`을 올린다.

### 2.6 AI로 제안(페르소나와 프로필)

페르소나 편집기의 "AI로 제안" 카드는 몇 마디 설명으로 페르소나와 프로필 초안을 만든다. 2026-10-30에 C2보다 먼저, 지금의
페르소나 형식 위에 만들었다:

- 사람은 설명(1,000자 이하)을 쓰고 자리(전문가, 제안자, 비평가, 판정자), 프로젝트 종류(코드, 운영, 디자인), 모델(자동,
  claude, codex, agy)을 고른다. `POST /api/personas/suggest`가 `guardian.py --persona-suggest`(`persona_suggest.py`)를
  실행한다: `LLMRunner.run_prompt`로 모델 한 턴, 도구 없음, 빈 작업 디렉터리, 역할 머리말 없음.
- 프롬프트에는 설명, 가이드 규칙(어떻게가 아니라 누구, 700자 이하, 호스트 수·버전·경로·도구 이름·자율 주장 없음, 실존
  인물·브랜드 없음), 같은 자리의 기본 제공 페르소나 최대 두 개(같은 종류 먼저)를 문체 예시로 싣는다. 폼에 시스템
  프롬프트가 이미 있으면 고칠 초안으로 함께 보낸다.
- 답은 JSON으로 읽어 아는 필드만 남기고, 빈 id(이미 있으면 `_2`, ...)와 자리의 역할 이름을 붙여 `validate_persona`로
  확인한다. 가이드 경고(700자 초과, 도구 이름, 자율, 호스트 수)는 초안과 함께 돌아오며 막지는 않는다.
- **아무것도 저장하지 않는다.** 초안은 폼을 채운다. 기존 페르소나는 id와 도구를 지킨다(모델은 도구를 고르지 않는다).
  사람이 읽고 고친 뒤 평소처럼 저장한다.
- 허브에서는 한 번에 하나만 돈다(두 번째 요청은 409). 제한 시간 5분. 종료 코드 5(쓸 초안 없음, 또는 답한 LLM CLI 없음)는
  502다.
- 프로필(`tagline`, `look`)은 이제 페르소나 파일의 선택 필드 `profile`로 저장한다. 보여 주기만 하고 에이전트에게 보내지
  않는다. `look`은 초상 생성기(2.4)가 쓸 값이다.

## 3. 페르소나 정형화 가이드

한도는 저장할 때(`validate_persona`)와 기본 제공분에 대한 CI 린트로 확인한다.

**C1, C2 전까지(지금의 형식).** 페르소나는 아직 자유 텍스트 `system_prompt` 하나이고, 엔진에 역할 카드가 없으므로 자리
규칙과 근거 형식도 그 안에 있다. 새 페르소나는 C1이 그 부분을 나머지를 건드리지 않고 떼어 낼 수 있게 쓴다: 캐릭터를
먼저(정체, 전문 분야, 관점, 먼저 볼 것, 남에게 넘기는 것), 그다음 자리 규칙은 두 문장 이하로, 다시 쓰지 말고 같은 자리의
기본 제공 페르소나에서 그대로 옮긴다(린트는 반복 문장을 찾고, C1은 정확한 문장으로 옮긴다). 전체는 700자 이하.

**린트(`cli/llm-agent/persona_lint.py`).** 경고만 한다. CI를 실패시키지 않고 저장도 막지 않는다.

| 수준 | 규칙 | 뜻 |
|---|---|---|
| `warn` | `length`(700 초과), `autonomy`, `host-count`, `version`, `path`, `env` | 어느 형식에서든 틀림. `POST /api/personas`와 제안 단계가 경고로 돌려준다 |
| `move` | `tool`, `grading`, `verdict`, `citation`, `protocol` | 자리 규칙, 근거 형식, 도구 이름: C1까지는 허용, C1이 옮길 것으로 보고 |
| `note` | `length`(501-700) | 길지만 한도 안 |

세 개 이상의 페르소나가 글자 그대로 되풀이하는 문장(역할 카드 후보)도 보여 준다. 실행은
`python3 cli/llm-agent/persona_lint.py`(`--json`, 허브의 사용자 페르소나까지는 `--custom`). `scripts/ci.sh python`은
`warn` 줄과 요약을 출력한다.

| 필드 | 형식 | 한도 |
|---|---|---|
| `identity` | 명사구 하나, "당신은 ...입니다"를 완성 | 120자 |
| `expertise` | 명사구 1-4개 | 각 60자 |
| `stance` | 1-2문장: 무엇을 최우선으로 하고 무엇을 양보하는지 | 200자 |
| `checks` | 1-5개, 출력 지시가 아니라 살펴볼 대상 | 각 80자 |
| `boundaries` | 0-3개, 남에게 넘기거나 요구하지 않는 것 | 각 80자 |
| 렌더링된 페르소나 | 블록 전체 | 700자, 500자 초과 시 경고 |

내용 규칙:

1. **어떻게가 아니라 누구.** 출력 형식, 등급 표시(`[차단]`, 높음/중간/낮음), 판정 용어, 인용 문법(`파일:줄`, `[#번호 ...]`),
   도구 이름(`ops:`, `jev_mcp:`)을 쓰지 않는다. 그것은 역할 카드와 종류 프로토콜의 몫이다. 린트는 `persona` 안의 이런
   패턴을 거부한다.
2. **변하는 사실을 쓰지 않는다.** 호스트 수, 버전 번호, 프롬프트 버전, 이 저장소의 파일 경로, 환경 변수를 넣지 않는다.
   프로젝트 사실은 캐릭터가 아니라 프로젝트에 둔다.
3. **자율 주장 금지.** "스스로 실행" 같은 표현을 쓰지 않는다(기존 `NoAutonomyTests` 유지).
4. **관점은 차이를 만들어야 한다.** 같은 자리의 두 캐릭터는 `stance`나 `checks`가 달라야 한다. 아니면 같은 캐릭터다.
   검토에 영향이 없는 성격 단어("명랑한", "엄격한")는 관점이 아니다.
5. **경계는 겹침을 막는 것이지 일을 막는 것이 아니다.** 관심사를 다른 자리에 넘길 때 쓰고, 사용자의 요청을 금지하는 데
   쓰지 않는다.
6. **한 언어.** 페르소나는 프롬프트 언어로 쓴다. `name`과 `profile`은 보이는 문구이므로, 기본 제공분은 대시보드 카탈로그를
   따른다.

한도를 넘어야 하는 캐릭터는 두 캐릭터이거나, 다른 곳에 있어야 할 자리·프로젝트 규칙을 싣고 있는 것이다.

## 4. 역할 카드(엔진 소유)

역할 카드는 자리와 프로젝트 종류별 짧은 엔진 텍스트로, 지금 기본 제공 페르소나들이 반복하는 내용에서 뽑는다:

| 자리 | 공통 카드(모든 종류) | 종류별 추가 |
|---|---|---|
| expert | 읽은 근거로 주문에 답하고, 가장 작은 변경과 되돌리는 방법을 제안 | ops: 가장 덜 파괴적인 것, 카탈로그 조치 우선 |
| critic | 깨지는 지점을 찾고, 지적마다 시나리오와 심각도, 문제가 없으면 분명히 없다고 | ops: 인용한 해악이 있을 때만 `[차단]`, 나머지는 `[권고]`; design: 구절 인용 |
| judge | 제안과 비판을 근거에 비추어 따지고, 확인된 단계만 승인, 금지 조건을 지어내지 않음 | ops: `[권고]`는 checks로, `[차단]`만 계획을 바꿈 |
| verifier, stage, side | 기존 흐름 텍스트(`VERIFY_TASK` 등) | — |

도구에 묶인 판정자 규칙(계획 규칙, `bundles`, 배치 규칙: 판정자가 도구를 가질 때만 붙음)은 지금처럼 엔진에서 도구별로
붙이며 캐릭터에 두지 않는다.

  제공분마다 렌더링 길이와 규칙 위반을 보고한다. 기준선을 얻는다. 2026-10-31 구현, 같은 날 `670d6c7`로 배포(구현 메모 참고).

  유지했고 `fleet-provision`은 시험 토론으로 보정했으므로, C1은 코드 팀부터 시작하고 ops 팀은 샌드박스 시험 토론 뒤에만

- **C3 명단과 재사용.** 팀 자리 `focus`. 중복된 기본 제공분(안전 검토자 세 벌, ops 판정자 네 벌의 공통 문장)을 자리 초점이
  붙는 캐릭터로 합친다. 합칠 때마다 골든 덤프와 시험 토론 한 번으로 확인한다.

  페르소나 필드마다 입력란 하나와 실시간 글자 수, 고른 팀 자리에 대한 조합 프롬프트 미리보기를 갖는다. 이벤트 카드는 자리

## 6. 운영자가 정할 것

1. **저장소.** 권장: 저장소 하나와 id를 유지(`configs/personas`, `/api/personas`)하고 `format: 2`를 더한다. "캐릭터"라는
   말은 대시보드와 문서에서 쓴다. 대안: 새 `configs/characters/` 저장소와 API(이름이 깔끔하지만 이행 기간에 저장소가 둘).
2. **길이 한도.** 권장: 렌더링 700자, 500자 초과 시 경고(지금 중앙값이 자리 규칙을 포함해 약 500자이므로 그것을 뺀 캐릭터는
   넉넉히 들어간다).
3. **프로필.** 2026-10-30 운영자 결정: 캐릭터는 gemini나 codex로 만든 초상을 가질 수 있다(2.4절). 아이콘(정해진 집합)과
   색 토큰은 대체로 남는다. 열린 것: (a) 스타일: 초상이 실존 인물로 오인되지 않도록 사진풍보다 일러스트 하우스 스타일 하나를
   권장; (b) 기본 후보 수(권장 2); (c) 기본 제공 캐릭터에 커밋된 초상을 둘지.
4. **캐릭터와 모델.** 권장: 캐릭터는 제공자나 키를 고르지 않는다. 그것은 계속 자리의 몫이다(`agent-seats-keys.md`). 나중에
   구속력 없는 `preferred_providers` 힌트는 둘 수 있다.
5. **말투.** 권장: 페르소나에 말투를 넣지 않는다(토큰을 쓰고 검토를 치우치게 할 수 있음). 개성은 프로필에 둔다.
