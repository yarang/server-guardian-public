# 다각도 토론: 독립 제안과 블라인드 비판 (설계)

[English](multi-perspective.md) | 한국어

상태: 결정 10건 확정(2026-10-18, jev를 통해 결정, "결정 과정" 참조). P1과 P3는 구현됐고(기본 꺼짐, 쓰는 팀 없음) P2는 만들어서 허브에서 한 번 돌렸다(2026-10-19): 옵트인, "구현 메모" 참조.
배경: "토론 에이전트를 서로 다른 서버에서 돌려야 더 많은 각도로 분석하는가?"라는 질문. 논의의 결론은 관점의 다양성이
**논리적 분리**(모델, 페르소나, 근거, 독립성)에서 나오고, 실행 호스트에서는 나오지 않는다는 것이다.
이 문서는 논리적 부분을 설계한다. 물리적 분산은 범위 밖이다("범위 밖" 참조).

## 문제

지금 토론의 한 라운드는 하나의 사슬이다. **Expert 한 명이 초안을 쓰고 → Critic 패널이 그 초안을 읽고 → Judge가 판정한다**
(`debate_engine.py`의 라운드 루프). 다룰 수 있는 각도를 제한하는 것이 두 가지 있다.

1. **하나의 초안이 모든 것을 고정한다.** 모든 Critic과 다음 라운드의 Expert는 같은 첫 제안에서 출발한다. Critic끼리는
   독립이지만(서로의 비판을 보지 않는다) 모두 Expert의 틀에 묶여 있다. 틀 자체의 결함은 그 틀을 이미 받아들인 검토자가
   찾기 어렵다.
2. **구성이 다양해 보여도 실제로는 아닐 수 있다.** 페르소나 세 개가 모두 같은 provider에서 돌면 그 provider의 사각지대를
   공유한다.

엔진이 이미 잘하고 있고 이 설계가 유지하는 것: 패널 병렬 실행(`_ask_critics`), 패널 비판은 LLM 요약 없이 원문 그대로
이어 붙이기, Judge는 책임지는 작성자 한 명, 대체(fallback) 답이 하나라도 있는 라운드는 `UNVERIFIED`
(`docs/design/debate-teams.ko.md`의 "규칙").

## 아이디어: 펼친 뒤 모은다

```
1라운드   주 Expert ─┐
          제안자 B  ─┼─ 초안을 병렬로 작성, 서로의 초안을 보지 않음        (신규)
          제안자 C  ─┘
                     ▼
          Critic 패널이 모든 초안을 중립 라벨로 읽음                      (프롬프트 변경)
                     ▼
          Judge 판정 (초안과 비판을 읽고 결정 하나를 작성)
2라운드~  주 Expert 혼자 초안들과 비판을 바탕으로 통합 제안 하나를 작성,
          나머지는 지금과 같음
```

- **독립 제안.** 주 Expert(지금의 `expert`) 외에 팀이 `proposers`를 최대 2명 더 둘 수 있다. 각자 같은 과제에 자기
  세션에서 병렬로, 다른 초안을 보지 않고 답한다.
- **LLM 병합 없음.** 초안은 Critic과 Judge에게 `### Proposal A`, `### Proposal B`... 형태로 원문 그대로 간다(패널 비판과
  같은 규칙). 통합은 다음 라운드에서 주 Expert가 맡으므로, 제안과 승인은 각각 책임지는 작성자가 한 명이다.
- **블라인드 비판.** Critic은 페르소나·provider 이름 없이 중립 라벨만 본다. 초안 순서는 라운드 번호에 따라 돌려서 "A"가
  항상 주 Expert가 되지 않게 한다. 어느 에이전트가 어느 초안을 썼는지는 기록(transcript)에 남는다.
- **효과가 있는 곳에서만 펼친다.** 추가 초안은 스레드의 첫 라운드(와 후속 지시 직후)에만 쓴다. 이후 라운드는 모으는
  단계여서 비용이 라운드 수만큼 곱해지지 않는다.

## 결정 (2026-10-18 확정)

| # | 항목 | 권장 기본값 | 다른 선택 |
|---|---|---|---|
| 1 | 각도를 어디서 얻는가 | 팀 파일의 추가 `proposers`, 각각 `Member`(페르소나 + providers). 기본은 없음이라 기존 팀은 지금과 똑같이 동작 | 동급 주 Expert 여러 명 ("책임지는 작성자 한 명" 원칙이 깨짐) |
| 2 | 몇 명까지 | 추가 제안자 0-2명(`MAX_PROPOSERS = 2`), 초안은 최대 3개 | Critic 패널처럼 4명까지. 초안이 늘면 Critic 프롬프트가 길어지고 Judge 입력이 커지는데 도움이 된다는 근거가 없음 |
| 3 | 초안 병합 | LLM 병합 없음. 원문 그대로 라벨을 붙이고, 2라운드부터 주 Expert가 통합 | Critic 앞에 LLM 종합 단계 (순차 호출이 늘고 근거가 흐려짐) |
| 4 | 블라인딩 | Critic에게는 중립 라벨(`Proposal A/B/C`), 라운드마다 순서 회전, 실제 이름은 기록에만 | 이름 공개(권위에 끌림), 호출마다 무작위 순서(재현 불가) |
| 5 | 추가 초안을 쓰는 시점 | 스레드의 첫 라운드와 후속 지시 뒤. 2라운드부터는 통합 | 매 라운드 (비용 × 라운드 수, 초안이 계속 벌어짐) |
| 6 | 제안자가 내장 문구로 대체될 때 | **하나라도 대체되면 라운드 전체 `UNVERIFIED`**, Critic 패널과 같은 규칙 (jev 0.90. 이 문서의 첫 초안은 다른 선택을 권장했다) | 추가 초안은 빼고 기록(`fallback`, 경고, Judge에게 "초안 3개 중 2개 사용 가능" 안내)하며 라운드는 검증됨 유지: provider 한도에는 더 튼튼하지만, 설정보다 각도가 적은 토론이 검증된 것으로 셈해짐 |
| 7 | 다양성 점검 | 팀의 모든 멤버가 한 provider로 해석되면 `--teams`와 대시보드가 경고("각도가 독립적이지 않을 수 있음") | 점검 없음 |
| 8 | Critic이 초안을 읽기 전에 하는 사전 분석 | **이 설계에 넣지 않음.** 제안자 평가 뒤에 따로 평가(4단계, P4) | 지금 같이 만들기 |

## 팀 파일

`proposers`는 선택 항목이고, 비어 있으면 저장되는 스냅샷에 나타나지 않는다(`code_tools`와 같은 방식). 그래서 기존 스레드와
스냅샷의 모양이 그대로 유지된다.

```json
{
  "id": "multi-angle",
  "expert":    {"persona": "domain_architect", "providers": ["claude"]},
  "proposers": [{"persona": "ops_sre",         "providers": ["codex"]}],
  "critic": [{"persona": "critic_redteam", "providers": ["codex"]},
             {"persona": "devops_specialist", "providers": ["agy"]}],
  "judge":  {"persona": "jev_mcp_decision", "providers": ["claude"]}
}
```

기존 팀 규칙과 같은 방식의 규칙:

- 페르소나는 expert와 proposers 전체에서 겹칠 수 없다(페르소나가 세션 키의 접미사이기 때문, 아래 참조).
- 제안자의 세션 키는 `Domain Expert:<persona>`이다. 주 Expert는 기존 `Domain Expert`를 그대로 써서 이미 있는 스레드의
  세션이 이어진다(`Lineup.session_key`, Critic 패널과 같은 방식).
- 제안자도 다른 멤버처럼 `code_tools: "mcp"`를 쓸 수 있다. 인용 검사는 세션 키 단위라서 제안자마다 자기 기록을 가진다.
- ops·design 프로젝트에서는 종류별로 평가하기 전까지 제안자를 경고와 함께 무시한다(평가는 결함 말뭉치가 있는 design
  종류부터 시작하고, ops에는 아직 없다).

## 엔진 변경

모두 `cli/llm-agent` 안이다. Go 허브와 API는 바뀌지 않는다(허브는 CLI를 띄우기만 한다).

| 파일 | 변경 |
|---|---|
| `team_manager.py` | `Lineup.proposers`, 파싱·검증(페르소나 중복 금지, `MAX_PROPOSERS`, provider 다양성 경고), 비어 있지 않을 때만 스냅샷에 포함, 제안자의 `session_key` |
| `debate_engine.py` | `_ask_critics`를 본뜬 `_ask_proposers`(스레드 풀, 초안마다 자기 trace); 라운드 루프가 초안마다 `draft` 라벨이 붙은 `EXPERT_ROLE` 기록을 하나씩 남김; Critic과 Judge의 프롬프트가 라벨 붙은 초안을 나열; `start_round`는 Expert 항목 수가 아니라 서로 다른 라운드 수를 셈(`len([t for t in transcript if role == EXPERT_ROLE])`는 두 번 센다); 2라운드부터 주 Expert에게 초안들과 합친 비판을 줌 |
| `debate_events.py` / 이벤트 | `debate_started.members`에 제안자 포함. `agent_*` 이벤트는 이미 `agent`, `agent_name`을 담고 있어 lane이 저절로 생김 |
| `thread_digest.py` | 변경 없음(role 기준. 다중 초안 라운드 테스트로 확인) |
| `debate_report.py`, `agentMonitor.ts` | 변경 없을 것으로 예상: 둘 다 agent와 role로 구분하며 패널도 같은 방식이다. 한 라운드에 Expert 둘인 테스트로 확인 |
| 대시보드 팀 편집기 | 나중(P3): Critic 패널 옆에 제안자 목록과 provider 다양성 경고 |

호환성: `proposers`가 없는 팀은 지금과 똑같은 코드 경로를 탄다(같은 프롬프트, 같은 기록). 다중 초안 문구는 별도 분기라서,
공유 프롬프트 줄이 바뀔 때만 `RETRIEVAL_PROMPT_VERSION`을 올린다. 이 변경 전에 시작한 스레드도 `start_round`를 서로 다른
라운드로 계산하므로 이어서 진행할 수 있다.

## 자원 모델

병렬 에이전트는 허브(2 OCPU, 12 GB)에서 별도 CLI 프로세스로 돈다. 이 설계는 첫 라운드의 동시 프로세스를 Critic 앞에서
최대 3개로, Critic 단계에서 최대 4개로 늘리고, 거기에 `MaxRunning`(기본 2)개의 토론이 겹친다. 기본값을 바꾸기 전에 알아야
할 것이 두 가지다.

- **허브 부하.** 허브에서 도는 `claude`/`codex` 프로세스 하나의 메모리와 CPU를 아직 측정하지 않았다(P0).
- **provider 한도.** 평가 2의 첫 실행은 135회 중 107회가 claude CLI 실패(사용 한도로 추정)로 내장 대체 답을 내서 무효였다
  (`docs/analysis/2026-10-13-retrieval-eval2/plan.ko.md`, "재실행"). 한 계정으로 동시 호출이 늘면 이런 일이 더 잘 생긴다.
  결정 6에 따르면 제안자 하나가 실패해도 그 라운드는 `UNVERIFIED`가 된다. 그래서 병렬 상한을 P1에 넣는다.
  `GUARDIAN_MAX_PARALLEL_AGENTS`(토론당 기본 4, 제안자와 Critic이 같은 제한된 풀을 쓴다). 한도 실패 때문에 다중 초안
  토론이 너무 취약하다고 평가에서 나오면 결정 6이 가장 먼저 다시 볼 항목이다(다른 선택은 표에 있다).

## 도움이 되는지 어떻게 아는가 (평가)

초안이 많으면 문제를 더 찾는다는 증거는 아직 없다. 기본값으로 삼으려면 평가 2와 같은 방식으로 측정해야 한다(운영 데이터
디렉터리가 아니라 `~/guardian-eval` 아래 별도 데이터 디렉터리).

- **과제 종류.** 평가 1-2의 검색 질문은 정답이 하나여서 다양성의 효과를 보여줄 수 없다. **결함을 심은 검토 과제**를 쓴다.
  결함 말뭉치(`artifact_corpus.py`)에서 만든, 결함 3-5개를 한꺼번에 심은 산출물이나 작은 임시 저장소다. 말뭉치의
  `low-contrast`와 `false-claim` 종류는 탐지기가 없고 토론으로 측정하기로 했던 것이다. 산출물 변형이 동작함을 확인한 뒤
  코드 변형(버그를 심은 임시 저장소)을 추가한다.
- **구성.**

  | | 구성 | 답하려는 질문 |
  |---|---|---|
  | C0 | 지금의 기본 팀 | 기준선 |
  | C1 | 주 Expert + 제안자 1, 같은 페르소나·같은 provider | 연산량만 늘려도 도움이 되는가 (대조군) |
  | C2 | 주 Expert + 제안자 1, 다른 페르소나·같은 provider | 관점의 효과인가 |
  | C3 | 주 Expert + 제안자 1, 다른 페르소나·다른 provider | 모델의 효과인가 |
  | C4 | C3에서 Critic에게 이름 공개 | 블라인딩이 중요한가 |

- **지표.** 주 지표: 심은 결함의 재현율(최종 결정과 비판 전체의 합집합). 그 밖에 틀린 주장, 인용 실패, 합의까지의 라운드
  수, 소요 시간, 바이트와 단계 수(이벤트에 토큰은 없다), 대체 답 횟수. 구성·과제마다 3회, 라벨을 섞은 블라인드 채점이며,
  대체 답이 한 번이라도 있는 실행은 버리고 다시 돌린다(평가 2와 같음).
- **판단 기준 (결정 10).** C2 또는 C3가 C0와 C1 모두보다 평균 재현율이 C0의 표준편차 하나 이상 높고, 평균
  소요 시간 증가가 50 % 이하일 때만 해당 프로젝트 종류의 기본값으로 삼는다. 아니면 팀 옵션(opt-in)으로 둔다.

## 단계

| 단계 | 내용 | 모델 필요 |
|---|---|---|
| P0 | 허브에서 측정(읽기 전용): LLM CLI 프로세스 하나의 메모리·CPU, 최근 `events.jsonl`의 단계별 소요 시간과 합의까지의 라운드 수 | 아니오 |
| P1 | `team_manager` + `_ask_proposers` + 프롬프트 + 병렬 상한, 스텁 provider 테스트 | 아니오 |
| P2 | 결함 심은 과제 세트와 평가 도구(C0-C4) | 만들기: 아니오, 실행: 예 |
| P3 | 대시보드 팀 편집기, `--teams` 다양성 경고 | 아니오 |
| P4 | 평가로 기본값 결정, 그 뒤 Critic 사전 분석(결정 8) 평가 | 예 |

기능이 기본적으로 꺼져 있으므로 P1은 P0가 끝나기 전에 시작해도 된다. 허브에서 켜는 것은 P0 뒤에 한다.

## 결정 과정

열 가지 결정을 문제, 제약, 선택지와 함께 jev(`jev_ask`, 모델 jev-1.13.0)에 물었다. 질문은 표의 행에 교차 확인 둘(지금은
물리적 분산 없음, 채택 기준)을 더한 것이다. 결과:

| 결정 | jev의 선택 (확률) | 액션 수준 |
|---|---|---|
| 1 proposers | `proposers` (1.00) | act |
| 2 인원 | 0-2명 (0.50, 최다 득표) | abstain: 작성자의 선택으로 유지. 영향이 작고 상수 하나로 바꿀 수 있음 |
| 3 병합 | 원문 그대로 (1.00) | act |
| 4 블라인딩 | 중립 라벨, 회전 (0.93) | act |
| 5 시점 | 첫 라운드 (0.83) | review: 수용 |
| 6 대체 답 | 하나라도 대체되면 `UNVERIFIED` (0.90) | act: **첫 초안의 권장과 달랐고 채택함** |
| 7 다양성 점검 | 경고 (0.58, 최다 득표) | abstain: 작성자의 선택으로 유지. 경고일 뿐임 |
| 8 사전 분석 | 미룸 (0.99) | act |
| 교차 확인: 물리적 분산 | 지금은 아님 (1.00) | act |
| 교차 확인: 채택 기준 | 측정 후 (1.00) | act |

jev는 질문에 적힌 내용만 평가하므로 답은 제시한 선택지만큼만 믿을 수 있다. 2번과 7번은 jev의 확신 없이 정했고 위 표에
표시했다.

## 범위 밖

- **다른 노드에서 에이전트 실행.** 물리적 분산은 실행 호스트별 세션 고정과 자격 증명, 코드와 프롬프트의 허브 밖 이동,
  버전 불일치를 더하고, 확정 결정 "fleet worker 없음"(CLAUDE.md)과 충돌하며, 그것만으로는 다양성을 만들지 않는다.
  P0에서 허브가 포화로 나타나거나 별도 계정·한도가 필요할 때만 다시 검토한다. 분산 없이도 잘 병렬화되는 독립 작업은 코드
  위키 생성과 감사 샤드이며, 이는 별도 주제(허브 안 스레드 풀)다.
- **팀 대 팀** (`debate-teams.ko.md`)과 **초안을 병합하는 LLM**.
- **큐, 그래프 DB, 벡터 인덱스** (확정 결정).
- Judge가 제안할 수 있는 것과 jev 게이트의 변경. 결정을 쓰는 것은 여전히 Judge뿐이며, 다중 초안은 Judge가 읽는 것을
  바꿀 뿐 책임지는 범위는 바꾸지 않는다.

## 위험과 열린 문제

- 프롬프트가 길어진다: Critic과 Judge가 초안을 최대 3개 읽는다. 검색 예산은 결정으로 무제한이지만 긴 입력은 주의를
  흩뜨릴 수 있다. 평가에서 바이트를 기록하고 Judge의 형식 오류를 본다.
- 초안 순서의 편향은 회전으로 줄이지만 없애지는 못한다.
- 주 Expert가 통합할 때 다른 초안을 무시할 수 있다. Judge가 초안을 직접 읽고 기록에도 남으므로, 무시된 초안은 스레드를
  읽는 사람에게 보인다.
- 결함 말뭉치는 결함 발견을 시험할 뿐 설계의 질을 시험하지 않는다. 거기서의 이득은 열린 설계 질문에 대해 아무것도
  말해주지 않으므로, 측정 전까지 그런 질문에는 다중 초안을 옵션으로만 둔다.

## 구현 메모

P1과 P3는 구현되어 스텁 provider로 테스트했다(2026-10-18). 허브에는 아무것도 켜지 않았고 `proposers`가 있는 팀도 아직
없다. P2는 하네스를 만들어 허브에서 한 번 돌렸다(마지막 메모 참조).

- **P1(엔진).** `Lineup.proposers`(0~2명, `MAX_PROPOSERS`)는 비어 있으면 스냅샷에 없다. 그래서 없는 팀은 지금과 같은
  코드 경로를 타고 리드의 프롬프트는 바이트 단위로 같다(`RETRIEVAL_PROMPT_VERSION` 불변, 조건부 문구만 추가).
  초안 라운드는 `run_debate` 호출마다 첫 라운드라서 후속 지시도 다시 초안을 쓴다. 초안은 `Domain Expert` 기록 항목
  하나씩이다. DB는 (라운드, 에이전트, 역할, 내용, provider)만 저장하므로 중립 `draft` 라벨은 결과·이벤트·보고서에만
  있고 저장된 스레드에는 없다.
- **병렬 상한.** `GUARDIAN_MAX_PARALLEL_AGENTS`(기본 4)는 초안 단계와 비평가 단계의 스레드 풀을 각각 따로 제한한다.
- **익명성은 첫 비평에만 적용된다.** 초안 라운드의 비평가와 판정자는 중립 라벨(라운드마다 회전)을 보지만, 나중에 새로
  시작하는 세션(새 비평가 세션의 2라운드, 후속 지시)은 스레드 기록을 읽고 거기엔 초안 작성자의 실제 이름이 있다.
  첫 라운드 밖의 익명성은 주장하지 않는다. C4(`GUARDIAN_DRAFT_NAMES=1`, 제목에 작성자 표시)가 그 영향을 잰다.
- **경고.** 초안 작성자 provider가 모두 같으면 검증과 `--teams`에서 경고하고, 설치되지 않은 provider는 다른 멤버와
  같게 경고한다. 초안 작성자 누구든 내장 폴백이면 그 라운드는 `UNVERIFIED`다.
- **P3(대시보드).** 팀 편집기에 전문가와 비평가 패널 사이의 "추가 제안자" 카드(상한은 `catalog.max_proposers`, 기본 2,
  제안자가 있을 때만 페이로드에 `proposers`)를 두었고 팀 카드가 목록을 보여 준다. 문구는 두 카탈로그에 모두 있다.
  `config_ops`가 보고하고 `--teams`가 `draft :` 줄을 출력한다.
- **P2(하네스, `cli/llm-agent/proposer_eval.py`, 모델 없음).** 결함 4개짜리 과제 5개(코퍼스의 broken-svg·low-contrast·
  dead-link·missing-section·false-claim 분류, 중복 없음), 설정 C0~C4(제안자만 다른 팀 파일), 채점기를 만들었다. 채점기는
  자동 사전 채점(파일 이름과 핵심어, 상한값), 라벨을 섞은 블라인드 시트와 별도 키, 폴백 실행 폐기, 결정 10의 규칙을
  코드로 담는다. 편차: 팀 안에서 페르소나가 유일해야 하므로 C1은 리드 페르소나를 다른 id(`domain_architect_b`)로 복사한다.
  ops·design 프로젝트는 제안자를 무시하므로 산출물은 임시 **코드** 프로젝트의 파일로 검토시킨다. `--prepare DIR`가 과제·팀·
  페르소나·환경을 쓰고, 허브 실행(`~/guardian-eval` 아래 별도 데이터 디렉터리)은 아직 스크립트가 없으며 P0가 먼저다.
- **평가 실행(2026-10-19, `docs/analysis/2026-10-19-multi-draft-eval/results.ko.md`).** 쉬운 과제 3개는 천장에 닿아(5개
