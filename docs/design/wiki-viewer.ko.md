# 위키 뷰어: 시작할 수 있는 인덱스와 읽으면서 페이지 사이를 이동하기

[English](wiki-viewer.md) | 한국어

상태: 제안 2026-10-27, 결정 1-5는 같은 날 권장대로 승인. V0(페이지 링크), V1(인덱스, 읽기 화면), V2(`summary`, `links`), V3(단축키)는 구현해 배포했습니다(2026-10-28, `d84562c`). V4(읽기 | 파일 | 기록 세 모드, 결정 6, 2026-10-28 승인)는 구현해 배포했습니다(2026-10-28, `5a8df55`). 실제 브라우저 확인은 아직 없습니다.
기반 문서: `debate-code-index-wiki.md`의 "Layer 2. Code wiki"와 `code-wiki-coverage.md`(페이지 종류, 파일 보기). 이 문서는
대시보드가 페이지를 보여주는 방식만 바꿉니다. 페이지 저장 형식, 작성기, 증거 규칙은 바뀌지 않습니다.

## 1. 문제

허브의 저장소 주소를 고친 뒤(2026-10-27) 운영자가 위키를 읽을 수 있게 됐고, 첫 인덱스 화면에서 시작해 읽으면서 페이지 사이를
이동하는 뷰어를 요청했습니다. 지금은 다음과 같습니다.

1. **인덱스가 없습니다.** `#/debates/wiki`는 페이지 목록(그룹 페이지는 개요 아래에 들여쓰기)과 "페이지를 선택하세요" 카드를 나란히 보여줍니다.
   id, 상태 칩, 날짜는 보이지만 페이지가 무엇에 관한 것인지, 어디서 시작할지는 알 수 없습니다.
2. **페이지끼리 이어지지 않습니다.** 작성기는 모든 페이지의 마지막에 관련 페이지를 `[[id]]`로 쓰게 합니다(`wiki_build.py` 508, 553, 712, 722행).
   그런데 대시보드는 `[[id]]`를 링크로 바꾼 적이 없고, `report.ts`는 `http(s)`가 아닌 링크를 쓴 그대로 출력합니다.
   운영자 보고(2026-10-27): "wiki에 링크가 파싱되지 않아 링크가 눌러지지 않는다."
3. **읽는 화면에 위치감이 없습니다.** 경로(인덱스 > 개요 > 그룹), 이전/다음 페이지, 이 페이지를 가리키는 페이지 목록이 없습니다.
   좁은 화면에서는 목록과 페이지가 서로 다른 화면이고 돌아가기 링크 하나뿐입니다.
4. **페이지 동작이 페이지를 어지럽힙니다.** 다시 쓰기, 편집, 삭제가 모든 페이지의 머리 카드에 있는데 대부분의 방문은 읽기만 합니다.

## 2. 데이터가 이미 주는 것 (V1은 새 API 없음)

`GET /api/projects/{id}/wiki`는 페이지마다 `id`, `title`, `scope`, `author`, `updated`, `state`, `kind`를 줍니다. 페이지 보기에는
본문, `docs`, 낡음 상세, 생성된 지도가 더해집니다.

- **트리.** 그룹 페이지 id는 `<개요 id>--<이름>`(`GROUP_SEPARATOR`)이므로 부모는 첫 `--` 앞의 id입니다. `feature-*` 페이지는 부모가 없고,
  `dir`과 `overview`는 뿌리입니다.
- **순서.** 목록은 저장 순서(id 정렬상 `dir`이 `dir--part`보다 앞)로 옵니다. `KIND_ORDER`(`dir`/`overview`, `feature`, `group`)는 토론 첫 프롬프트의
  페이지 순서일 뿐이므로, V1이 `lib/wiki.ts`에서 자신의 인덱스 순서(각 뿌리 뒤에 그 그룹, 그다음 기능)를 계산합니다.
- **상태.** 페이지마다 `fresh | stale | broken`이므로 인덱스가 위키를 얼마나 믿을지 말해줄 수 있습니다.
- **관련 페이지.** 본문 안(`[[id]]`)에만 있습니다. 역방향 링크(누가 여기를 가리키나)는 모든 본문이 필요한데 목록에는 본문이 없습니다.

## 3. 설계

### 3.1 경로

| URL | 화면 |
|---|---|
| `#/debates/wiki` | **인덱스**(신규): 진입 화면 |
| `#/debates/wiki/<page>` | **읽기 화면**(본문과 위치, 이웃 페이지) |
| `#/debates/wiki?view=files`, `?file=<path>` | **파일** 모드: 파일 목록과 파일 보기(V4: 모드 선택에서 들어감) |
| `#/debates/wiki?view=history` | **기록** 모드(V4): 빌드 작업과 빌드를 시작하는 모든 동작 |

모든 이동이 해시 경로이므로 브라우저의 뒤로/앞으로는 지금처럼 동작하고, 새로고침해도 위치가 유지됩니다.

### 3.2 인덱스 화면

전체 너비, 구역이 세로로 이어지는 한 열입니다. 이 화면에는 왼쪽 페이지 목록이 없습니다.

1. **머리:** 프로젝트 전환, 검색 상자(제목, id, 범위를 거름), `새로고침`, `새 페이지`, `빌드`, 파일 보기 링크. 상태 줄에 "N 페이지, M개 확인 필요"와
   가장 최근 페이지의 날짜를 보여줍니다.
2. **주의**(`stale`/`broken`이 있을 때만): 해당 페이지를 상태 칩과 첫 이유(바뀐 파일, 깨진 인용)와 함께 보여줘서, 읽기 전에 무엇을 믿지 말지 알게 합니다.
3. **여기서 시작:** 뿌리(`overview`, `dir` 페이지)를 카드로 보여줍니다. 카드에는 제목, 종류, 상태 칩, 한 줄 범위, 아래 그룹 페이지 수가 있고
   V2부터 한 줄 요약이 더해집니다.
4. **설계 기능:** `feature-*` 페이지는 코드가 아니라 의도를 읽는 용도이므로 간결한 목록(제목, 상태)으로 둡니다.
5. **그룹**은 별도 구역이 아니라 자신의 개요 카드 안에(접힌 목록으로) 보여줍니다.

위키가 비어 있으면 기존 빈 상태 문구와 `빌드` 동작을 보여줍니다.

### 3.3 읽기 화면

- **위치 줄**(본문 위): `인덱스 › <개요> › <이 페이지>`. 각 부분이 링크입니다. 좁은 화면에서는 `‹ 인덱스`와 부모만 보입니다.
- **이웃**(본문 아래): 인덱스 순서(각 뿌리 뒤에 그 그룹, 그다음 기능)로 `‹ 이전`, `다음 ›`. 개요 페이지에는 그룹 페이지 목록(제목 포함)도 보입니다.
  위키 전체를 순서대로 읽을 수 있게 하는 링크입니다.
- **관련 페이지:** 본문의 `[[id]]`는 링크(V0)이며 작은 칩으로 보입니다. 목록에 없는 id는 점선으로 표시하고 누를 수 없습니다. 작성기가 삭제된 페이지를 말할 수 있기 때문입니다.
- **참조한 페이지**(V2): 본문이 여기로 링크하는 페이지들.
- **왼쪽 트리(넓은 화면만):** 인덱스 트리를 줄이고 접을 수 있게 한 사본으로, 돌아가지 않고도 이동하게 합니다. 지금의 목록을 대체합니다.
  좁은 화면에서는 보이지 않고 위치 줄이 그 일을 합니다.
- **동작:** `다시 쓰기`, `편집`, `삭제`는 머리 카드의 `페이지 동작` 메뉴 하나로 옮깁니다. 상태 칩, 작성자, 확인 시각은 계속 보입니다.
  각 동작의 행동(확인 대화상자 포함)은 바뀌지 않습니다.
- **목차와 인용 칩**은 구현된 그대로(`WikiNarrative`)입니다. 인용을 누르면 지금처럼 파일 보기로 갑니다.
- **스크롤:** 다른 페이지로 이동하면 맨 위로 가고, 뒤로 가기는 브라우저가 기억한 위치로 돌아갑니다.

### 3.4 좁은 화면

인덱스는 카드 한 열입니다. 읽기 화면은 위에 위치 줄, 아래에 이웃 링크를 둔 한 열이며 트리와 목차는 숨깁니다(목차는 이미 컨테이너 쿼리 기반).

### 3.5 키보드(선택, V3)

`[`와 `]`는 이전/다음 페이지, `g i`는 인덱스, `/`는 검색 상자로 이동. 입력창이나 대화상자에 초점이 있으면 꺼집니다.

## 4. 단계

| 단계 | 내용 | 서버 변경 | 완료 조건 |
|---|---|---|---|
| V0 | `[[id]]`가 페이지 링크가 되고, 모르는 id는 없는 페이지로 표시 | 없음 | 2026-10-27 구현, 테스트 통과 |
| V1 | 인덱스 화면, 위치 줄, 이웃, 페이지 동작 메뉴, 왼쪽 트리, 좁은 화면 배치, ko/en 문구 | 없음 | 운영자가 인덱스에서 시작해 링크를 따라 위키 전체를 넓은/좁은 화면에서 읽을 수 있음 |
| V2 | 목록 항목마다 `summary`(역할/의도 절의 첫 문단, 160자 이내)와 `links`(`[[id]]`로 찾은 id); "참조한 페이지"; 카드의 요약 | `code_wiki.py`의 `listing()`, `wiki_ops` 출력, `WikiPageSummary` | 브라우저가 모든 페이지를 읽지 않고도 역방향 링크를 보여줌 |
| V3 | 키보드 단축키, 트리 접힘 상태 기억 | 없음 | |
| V4 | 한 선택기 뒤의 세 모드(읽기, 파일, 기록); 빌드 버튼과 "새 페이지"는 기록에만; 빌드 작업 표 | 없음 | 읽기 화면에 빌드 버튼이 없고, 모든 빌드를 기록에서 시작하고 따라갈 수 있음 |

V1은 V2를 기다리지 않습니다. 요약이 없으면 카드는 범위 줄을 보여주고, "참조한 페이지"는 그냥 없습니다.

## 5. 규칙

- 뷰어는 페이지를 저장된 그대로 보여줍니다. 링크를 넣으려고 본문을 고쳐 쓰지 않으며, `[[id]]`는 인용 칩처럼 정화(sanitize) 뒤 DOM에서 링크로 바뀝니다.
- 페이지 id는 저장된 목록에서 옵니다. 링크는 `^[a-z0-9][a-z0-9-]{0,63}$`에 맞는 id로만 만듭니다.
- `localStorage`에는 편의(트리 접힘, 인용 숨김)만 두고, 없어도 페이지가 동작합니다.
- 새 문구는 두 카탈로그(`ko`, `en`)에 모두 넣습니다. 둘은 같은 모양입니다(`Messages` 타입).
- 위키 페이지를 읽는 것은 증거가 아니라는 점은 그대로입니다. 위키는 길 안내이고, 토론 에이전트는 `GUARDIAN_CODE_WIKI=1`이 아니면 위키를 보지 못합니다.

## 8. 구현 메모

### V0: 페이지 링크 (2026-10-27 구현, 2026-10-28 배포)

- `decorateNarrative`는 선택 인자 `PageLinks`(`known` id 또는 `null`, `href`)를 받습니다. `pre`, `code`, 링크 밖의 텍스트와 `[[id]]`만 담은
  인라인 코드는 `a.sg-wikilink`가 되고, `known`에 없는 id는 점선 `span.sg-wikilink-missing`이 됩니다. 페이지 목록이 아직 로드되지 않았을 때는
  `known`이 `null`이라 모든 id를 링크로 만듭니다(없는 id면 그 페이지 자신의 오류가 보입니다).
- 경로는 `hrefFor`로 만든 `#/debates/wiki/<id>`입니다. `WikiTab`이 목록의 id를 `WikiPageView`에 주고, 그것이 `WikiNarrative`에 `PageLinks`를 줍니다.
- 하지 않은 것: 링크는 페이지를 그릴 때 정해지므로 목록이 나중에 도착해도 id를 다시 표시하지 않습니다. URL로 바로 연 페이지는 다음 방문까지 없는 id가 링크로 보일 수 있습니다.
- **확인 못 한 것:** 작성기 프롬프트가 요구하는 `[[id]]` 형태만 처리했습니다. 저장된 본문은 읽지 못했으므로(그 세션에서 허브 접근 없음) 실제 페이지에
  상대 Markdown 링크(`[text](page-id)`, `[text](docs/x.md)`)나 `:N` 없는 경로가 있는지는 열려 있습니다. 있다면 `report.ts`가 아니라 위키 처리에서
  알려진 페이지 id는 페이지 링크로, 읽을 수 있는 저장소 경로는 파일 보기로 연결합니다.
- 일부러 건드리지 않은 것: `report.ts`는 `http(s)`가 아닌 Markdown 링크를 여전히 텍스트로 출력합니다. 에이전트의 토론 글이 임의 대상으로 링크를 만들면 안 되기 때문이며,
  내부 링크는 위의 위키 본문 처리만 만듭니다.

### V1: 인덱스와 읽기 화면 (2026-10-27 구현, 2026-10-28 배포)

- 순수 함수는 `lib/wiki.ts`에 있습니다: `buildWikiTree`, `indexOrder`, `pageNeighbours`, `parentOf`, `filterPages`, `attentionPages`,
  `referencedBy`. 부모는 `kind === 'group'`일 때만 구합니다(알려진 id 중 `--` 앞의 가장 긴 접두). 페이지 id 규칙이 손으로 만든 `dir` id의
  `--`를 허용하기 때문입니다. 개요가 없거나 루트가 아닌 개요를 가진 그룹은 스스로 루트로 보입니다.
- **인덱스 순서**는 각 루트 뒤에 그 그룹, 그다음 기능 페이지입니다. 설계 본문은 "루트, 기능, 그다음 그룹"이라 썼지만 그러면 그룹이 개요에서 멀어져
  차례로 읽기 어렵습니다. 이 순서는 목록의 순열입니다.
- `WikiIndex.tsx`가 시작 화면, `WikiReading.tsx`가 페이지를 둘러싼 틀(위치 줄, 트리, 이웃), `WikiTab.tsx`가 인덱스, 읽기 화면, 그대로인 파일 보기를
  고릅니다. 예전 두 열 목록과 "읽을 페이지를 선택하세요" 카드는 없어졌고, 카탈로그 키 `tab.selectPage`, `tab.pagesTitle`도 지웠습니다.
- 상태 줄에는 가장 최근 페이지의 날짜를 넣지 않았습니다. "페이지 N개, M개 확인 필요"와 확인 기준 커밋만 보입니다. 날짜는 각 페이지의 머리에서 봅니다.
- 검색 상자는 탭 머리 카드가 아니라 인덱스 본문에 있습니다. 머리 카드는 페이지 보기와 파일 보기와 함께 쓰기 때문입니다.
- **확인 필요** 구역은 상태 칩만 보여 줍니다. 목록에 이유(바뀐 파일, 깨진 인용)가 없고, 이유를 얻으려고 모든 페이지를 읽으면 페이지당 요청이 한 번씩 늘기
  때문입니다. 이유는 페이지 자신에서 봅니다.
- **페이지 동작**은 `role="menu"`가 아니라 펼침(`aria-expanded`)입니다. 세 버튼은 자기 라벨을 가진 보통 버튼으로 남습니다. 선택, Escape, 바깥 마우스
  누름으로 닫히고, 빌드 중에는 다시 쓰기가 비활성입니다.
- 다른 페이지로 가면 맨 위 앵커를 `scrollIntoView`로 보입니다. 이는 뒤로 갈 때 브라우저가 복원할 위치도 덮어쓰므로, 3.3의 "뒤로 가면 위치를 복원"은
  위키 페이지 사이 해시 이동에서는 지키지 않습니다.
- 트리는 넓은 화면에서만 보이고 페이지 요청이 아니라 목록으로 만듭니다. 목록이 로드되는 동안 읽기 화면에는 트리와 이웃이 없습니다. 목록 로드 실패는
  읽기 화면에 따로 알리지 않습니다(페이지는 자기 오류를 가집니다).
- V0의 "나중에 도착하는 목록" 메모는 닫혔습니다. `knownPages`가 목록에서 메모이즈되므로 `[[id]]` 링크는 목록이 도착한 뒤의 값으로 정해집니다.

### V2: `summary`와 `links` (2026-10-27 구현, 2026-10-28 배포)

- `code_wiki.py`의 `listing()`이 각 항목에 `kind`, `summary`, `links`를 더하고 `wiki_ops.list_pages`가 그대로 전달합니다. Go 에이전트는 CLI의
  JSON을 그대로 넘기므로(`respondConfig`) Go 변경은 필요 없었습니다.
- `page_summary`: **첫 섹션**(제목이 무엇이든. 작성기의 제목은 일정하지 않습니다)의 첫 문단, 최대 160자. 줄 인용(`` `path:12` ``), 그 뒤에 남은 빈 괄호,
  `[[id]]`의 대괄호를 지워서 카드가 문장처럼 읽히게 합니다.
- `page_links`: 나타나는 순서의 `[[id]]` id. 자기 자신, 모르는 id, 중복, 코드 블록 안은 뺍니다. 최대 60개.
- 요약은 목록을 요청할 때마다 저장된 본문에서 만들며 새로 저장하는 것은 없습니다.
- 허브가 `links`를 보내지 않으면(옛 허브) "이 페이지를 가리키는 페이지"는 비고, 카드는 범위 줄로 대신합니다.

### V3: 단축키와 기억하는 트리 상태 (2026-10-27 구현, 2026-10-28 배포)

- `hooks/useWikiShortcuts.ts`: `[`, `]`(이전, 다음), 1초 안의 `g` 다음 `i`(인덱스), `/`(검색). 키는 `event.code`로 맞추므로 한글 입력 배열에서도
  깨지지 않습니다. 조합 중, ctrl/meta/alt, input·textarea·select·편집 가능 요소, 대화상자가 열린 동안은 무시합니다. `preventDefault`는 핸들러가
  실행될 때만 부릅니다.
- 인덱스에서 `/`는 검색 상자에 초점을 줍니다. 페이지에서는 `#/debates/wiki?find=1`로 가고, 인덱스가 `find=1`을 보면 상자에 초점을 줍니다.
- 파일 보기에서는 단축키가 꺼집니다. 트리를 접은 상태는 `localStorage`(`sg.wiki.tree.collapsed`)에 try/catch로 감싸 보관하며, 없어도 동작합니다.

### V4: 읽기, 파일, 기록 모드 (2026-10-28 구현·배포)

- `lib/wiki.ts`: `wikiMode(page, query)`는 `read`(기본값), `files`(`?view=files` 또는 `?file=`), `history`(`?view=history`)를 고르고, 페이지 id가 있으면 항상 `read`입니다.
  `wikiJobs(jobs, project)`는 프로젝트의 위키 빌드 작업(`kind: 'code_wiki'`)을 최신순으로 남깁니다.
- `WikiTab`은 껍데기입니다: 프로젝트 선택기와 모드용 `SegmentedControl`, 빌드 배너와 "빌드 진행 중" 알림(모든 모드에 표시되므로 기록에서 시작한 빌드가 모드를 바꾼 뒤에도 보임),
  그 아래 모드별 본문. `hooks/useWikiBuild.ts`가 빌드 시작, 진행 중인 빌드 조회, 배너, 빌드가 끝났을 때의 목록 다시 불러오기를 맡습니다.
- `WikiHistory.tsx`는 예전에 인덱스 위에 있던 것을 담습니다: 다시 불러오기, 새 페이지, 첫 페이지 쓰기 또는 오래된 페이지 다시 쓰기, 모두 다시 쓰기, 설계 문서 페이지 쓰기, 큰 디렉터리 나누기
  (모두 확인 창 뒤), 프로젝트의 빌드 작업 표(작업, 상태, 시작, 소요, 모니터 링크), 주의가 필요한 페이지 목록. 읽기 화면은 페이지 동작 메뉴만 남기며, 거기서의 다시 쓰기는 여전히 `useWikiBuild`를 거칩니다.
- 설계와 다른 점: "이 파일을 다루는 위키 페이지"는 파일 보기에 이미 있어서 추가한 것이 없습니다. 문구 `files.browse`, `files.toPages`는 모드 선택기가 대신하므로 지웠습니다.
  좁은 화면에서는 페이지나 파일을 연 동안 머리글을 숨기고, 파일 보기에는 파일 목록으로 돌아가는 링크를 둡니다.
- 기록은 빌드 작업에 한정합니다. 위키 편집·삭제 핸들러는 대시보드가 읽을 수 있는 이력을 남기지 않아(목록에는 페이지별 `updated`만 있음) 페이지 편집과 삭제는 보여주지 않으며, 보이려면 읽기 API가 있는 서버 쪽 로그가 필요합니다.
